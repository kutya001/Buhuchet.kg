# PR Dependabot

Dependabot открывает PR по понедельникам. У такого PR `pr-policy` красный, пока Claude не проверил его и не дописал «Отчёт ревьюеров» с проверенным коммитом (docs/decisions.md п. О-40): это норма, а не поломка (docs/typical-mistakes.md № 24). PR с `.github/` сливает только заказчик.

## Порядок
1. Открытые PR от `dependabot[bot]`; у каждого — SHA головы PR (последний коммит).
2. **Что обновилось.** Пакеты и версии из описания и `git diff`; для мажорных версий — список ломающих изменений из заметок выпуска и где этот пакет у нас используется.
3. **Действия GitHub** (`.github/workflows`): новая ссылка — полный SHA, и он совпадает с тегом из комментария (`git ls-remote https://github.com/<действие> refs/tags/<тег>`); новые входы и выходы действия не ломают наши шаги; `permissions` не расширились.
4. **CI зелёный** на этом коммите: `check` и `docker-e2e`. Красный — скилл `ci-red`; ломающее изменение, которое правится кодом, — отдельным PR сессии, а не в ветку Dependabot.
5. **Отчёт.** В описание PR — раздел «## Отчёт ревьюеров» со строками `- spec-reviewer: соответствует — …`, `- security-reviewer: замечаний нет; критично: нет — …` и `- проверен коммит: <SHA головы>`. Новый пуш Dependabot в PR — проверка и строка с SHA заново.
6. Кнопку «Update branch» не нажимать: Dependabot обновит ветку сам. Сливать после больших PR недели, а не перед ними.
7. Заказчику — одна строка: какие PR проверены и можно сливать, какие нет и почему.

# Кусок модуля по ТЗ и прототипу

Одна задача = один кусок модуля = одна ветка = один PR. Источник истины — `spec/`, не память и не догадки.

## 1. План (до кода)
1. Прочитать задачу (GitHub Issue): модуль, кусок, раздел ТЗ, файл прототипа, что входит и что не входит, пункты приёмки.
2. Найти раздел в `spec/ТЗ Buhuchet.kg.md` (поиск по заголовку модуля) и файлы прототипа: `spec/prototype/src/js/modules/<модуль>.js`, нужные `spec/prototype/src/js/core/*.js`.
3. Выписать в план:
   - правила (каждое — с цитатой из ТЗ или ссылкой на функцию прототипа);
   - пункты приёмки «Как проверить, что всё работает», которые закрывает кусок;
   - данные: какие поля из `spec/data/demoDB.json` / `refDB.json` нужны;
   - права: какие из 37 прав и с какой областью («Свои / Все контрагенты»).
4. ТЗ и прототип расходятся или ТЗ молчит — не выбирать: скилл `spec-deviation`, вопрос в отчёт.

## 2. Таблицы — скилл `db-migration`
Схема Drizzle, миграция, `org_id` + RLS + тест изоляции, наполнитель демо-данных в `packages/db/src/seed/demo.ts`.

## 3. Правила — `packages/domain`
Чистые функции с тестами Vitest. Эталонные ответы — из прототипа (скилл `prototype-oracle`): тот же вход → тот же результат. Покрытие ≥ 80 %.

## 4. Методы API — скилл `api-endpoint`
Схемы Zod в `packages/shared`, право и область, запись в историю, тесты прав и изоляции против настоящего PostgreSQL.

## 5. Экран — скилл `ui-screen`
По прототипу, на общих компонентах `packages/ui`, тексты — в словарь.

## 6. Сквозные тесты
Каждый пункт приёмки — тест Playwright в `e2e/<модуль>.spec.ts`, проекты desktop (1280 px) и mobile (390 px). Строка в `docs/acceptance-map.md`: `- <пункт ТЗ> → e2e/<файл>.spec.ts › <название теста>`.

## 7. Сверка с прототипом
Снимки экрана продукта и прототипа рядом на ПК и телефоне (прототип: `python3 spec/prototype/build.py` собирает HTML, открыть в Playwright). Заметные отличия — в описание PR для приёмки заказчиком.

## 8. Проверка и PR
1. `pnpm check` — зелёный. Docker-проверка: `docker compose --profile app up -d --build --wait` и `E2E_BASE_URL=http://localhost:3000 pnpm test:e2e`, если менялись сборка, переходники или маршруты.
2. Запустить агентов `spec-reviewer` и `security-reviewer`; исправить найденное; их итог — в раздел «Отчёт ревьюеров» описания PR.
3. Расхождения с ТЗ — в `docs/deviations.md`.
4. PR по шаблону `.github/pull_request_template.md`; он сольётся сам, когда все проверки зелёные. Упала проверка — чинить и пушить снова, пока не станет зелёной.
5. Короткий отчёт заказчику: что сделано, как проверить на стенде, какие вопросы к ТЗ.

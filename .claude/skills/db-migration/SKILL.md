# Миграция базы

Миграции попадают в main по одной — через очередь по метке «миграция» (раздел ниже). Применённые миграции (уже в main) не меняются никогда — хук не даст.

## Порядок
1. Схема — `packages/db/src/schema/<модуль>.ts`, экспорт в `schema/index.ts` — одна строка по порядку модулей ТЗ.
   - Таблица организации: `orgId: uuid('org_id').notNull().references(() => organizations.id)`, `...timestamps()`, `version: recordVersion()`, `.enableRLS()` и политика `orgIsolation('<таблица>_isolation', t.orgId)`.
   - Деньги — `money('<поле>')` (тыйыны, bigint); сроки — `date('<поле>', { mode: 'string' })`; моменты — `timestamp(..., { withTimezone: true })`.
   - Индексы под фильтры списков: `org_id` первым столбцом; поиск по тексту — `gin_trgm_ops`.
   - Справочники платформы (общие для всех организаций) — без `org_id`, но запись только для администратора платформы через API.
2. `pnpm db:generate` → прочитать SQL в `packages/db/migrations/NNNN_*.sql` глазами: нет ли удаления данных, RLS включён, политика есть.
3. То, что Drizzle не генерирует (функции, триггеры, права, частичные индексы): `pnpm --filter @buhuchet/db exec drizzle-kit generate --custom --name=<что_делает>` и SQL руками. Новые таблицы получают права роли `buhuchet_app` автоматически (default privileges).
4. Запрещено в SQL: `auth.uid()`, `auth.jwt()`, схема `storage`, pg_cron, pg_net, Realtime; расширения — только pg_trgm, pgcrypto, citext (`pnpm check:portability`).
5. Изменение с потерей данных (удаление столбца, смена типа) — в два PR: сначала код перестаёт использовать, потом миграция удаляет. Откат — новой миграцией.
6. Тест изоляции в `packages/db/src/<модуль>.test.ts` или в тестах API — по образцу `packages/db/src/rls.test.ts`:
   - строки организации Б не видны в контексте организации А (`withOrgContext`);
   - нельзя изменить и создать строку чужой организации;
   - без контекста не видно ничего.
7. Демо-данные: функция в `packages/db/src/seed/demo-<модуль>.ts` из `spec/data/demoDB.json` с `DEMO_ORG_ID`, безопасная при повторе (`onConflictDoNothing`); в `seed/demo.ts` — только её вызов.
8. `pnpm db:migrate && pnpm db:seed --update && pnpm --filter @buhuchet/db test` — зелёные. CI проверяет, что `pnpm db:generate` после схемы ничего не создаёт (миграции не отстали от схемы).

## Очередь миграций
Миграции попадают в main по одной. Очередь держит открытый PR с меткой «миграция»: такой PR в репозитории один.
1. Пока задача в работе, миграции делаются как обычно (`pnpm db:generate`, ручные — `--custom`). Номер миграции окончательный только после слияния.
2. Когда всё остальное готово (тесты, отчёт ревьюеров, описание PR), проверить, нет ли открытого PR с меткой «миграция».
   - Есть — ждать его слияния (подписка на этот PR), а пока делать правки без базы.
   - Нет — поставить метку на свой PR и сразу проверить ещё раз. Метка у двух PR — её оставляет PR с меньшим номером, второй снимает.
3. С меткой обновить ветку с main слиянием (`git merge origin/main`, не rebase). Если в main появились новые миграции, свои пересоздать после них:
   - сохранить SQL своих ручных миграций (`--custom`) во временный файл;
   - вернуть папку миграций к main: `git restore --source=origin/main --staged --worktree packages/db/migrations` — файлы только из ветки (свои SQL и снимки) исчезают, журнал `meta/_journal.json` и применённые миграции становятся как в main, конфликт в журнале тоже решается так;
   - заново `pnpm db:generate`; ручные — заново через `--custom` с сохранённым SQL;
   - применённые миграции из main не трогать: их защищают хук и проверка `check` (`scripts/check-protected.mjs`). Если хук остановил команду — не обходить его, а спросить в треде «Архитектура и план разработки».
4. `pnpm check` и push. Пока метка стоит, схему не менять.
5. Метка уходит вместе со слитым PR. PR застрял (красная проверка, которую быстро не починить, замечание ревью) — снять метку, чтобы не держать очередь, и поставить заново, когда PR готов.
6. После слияния сообщить в тред «Архитектура и план разработки» номера миграций и таблицы (сверка `DevBuhUchet.kg/db/schema.json`).

Если правило нарушат, ошибка всё равно не попадёт в main: две миграции с одним номером конфликтуют в `meta/_journal.json` и снимке, автослияние не сливает ветку, отставшую от main, а CI проверяет, что `pnpm db:generate` после схемы ничего не создаёт.

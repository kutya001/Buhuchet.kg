# Сквозной тест

Сквозные тесты идут в CI на 6 машинах (п. О-49): 658+ тестов, у каждой машины своя база, но на одной машине тесты идут параллельно и видят записи друг друга, а тесты `*.shared` телефона идут сразу после тех же тестов ПК на том же сайте. Тест, который зависит от чужих данных или порядка, падает через раз и останавливает PR всех потоков. Номера — `docs/typical-mistakes.md`.

## Данные
1. Тест создаёт свои записи (контрагент, сотрудник, отчёт) со словом `uniqueWord('<приставка>')` (как в `e2e/contractors.spec.ts`; логины — `uniqueLogin`, ИНН — `uniqueInn`, чаты бота — `uniqueChat` из `e2e/helpers.ts`) и ищет, считает и ждёт только их: поиск по слову, фильтр, своя строка — а не «всего строк в списке» (№ 2).
2. Общая запись демо-организации или платформы (учётная политика, адрес страницы, настройки, справочники, словарь, функции модулей) — меняет только тест в `*.shared.spec.ts` и возвращает как было в `finally` (№ 7).
3. Ждать своё значение по уникальному названию — `toHaveText('…<своё слово>…')`, а не «блок появился»: общая память сервера (справочники лендинга — до минуты) может показать данные соседнего теста (№ 3).
4. Короткие числа не искать в тексте с номерами и UUID: проверять поле ответа API или строку целиком (№ 4). Даты — по Бишкеку (`timezoneId` проекта уже `Asia/Bishkek`), сроки в данных — от часов теста; конец месяца и года не ломает ожидание (№ 5).

## Тексты
5. Текст интерфейса — из словаря `GET /api/l10n` (как `e2e/l10n.spec.ts`) или общей частью, которая не меняется; копия длинной строки в тесте ломается при первой синхронизации с прототипом (№ 1).
6. Сменил текст, шаблон бота или формат (сумма, дата, номер) — `git grep -nF '<старая строка>' -- e2e packages apps` и поправить найденное в той же правке, в том числе в тестах других модулей.

## Вход, ожидания, время
7. Сменить вход при открытой странице — сначала `await page.goto('about:blank')`, потом `signIn` (как `e2e/display-name.spec.ts`, `e2e/org.spec.ts`): иначе запрос старой страницы стирает cookie нового сеанса (№ 6).
8. Без `waitForTimeout` и пауз: ждать состояние (`toBeVisible`, `toHaveText`, `expect.poll` с условием); подделка Telegram, очередь, расписание — тоже по условию (№ 8).
9. Тест укладывается в 30 с на медленной машине CI с запасом; длинный сценарий — разбить на тесты или `test.slow()` с причиной в комментарии (№ 9).
10. Каждый пункт приёмки — на ПК и телефоне; пропуск одного вида экрана — только `test.skip(!isMobile, '<причина>')`. `test.only`, `test.fixme`, закомментированные проверки — нельзя.

## Перед PR
11. `pnpm -s typecheck:e2e` и `pnpm -s check:e2e-list` (они же в `pnpm check`): тесты собираются и загружаются (№ 16, 17).
12. Сквозные тесты целиком локально не гоняются (CLAUDE.md). Правка анимаций, скриптов лендинга или оболочки — прогнать свой файл (1–2 файла этого экрана) на ПК и телефоне против `pnpm dev` (решение заказчика 14.11.2026, № 14):
    - база и хранилище — `pnpm setup:local` (в облачной сессии — Docker-образы с зеркала, см. память проекта);
    - `pnpm dev`, затем `pnpm test:e2e e2e/<файл>.spec.ts --project=desktop --project=mobile`;
    - файл `*.shared.spec.ts` — `--project=desktop-shared --project=mobile-shared --no-deps`.
13. Строка в `docs/acceptance-map.md`: `- <пункт ТЗ> → e2e/<файл>.spec.ts › <название теста>`.
14. Агент `test-reviewer` проверяет всё это и чужие тесты, которые задевает правка.

## Тест упал в CI
Скилл `ci-red`. Тест прошёл только со второй попытки — тоже падение (№ 10): сводка прогона и предупреждение на странице PR показывают его отдельно.

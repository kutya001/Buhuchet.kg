# Общая сборка

Заказчик просит сливать готовую работу нескольких потоков одним PR и одним полным прогоном CI. В #245 при такой сборке пропал помощник `pickContractor` одной ветки, старые тексты другой ветки сломали тесты третьей, и сборку собирали два треда (docs/typical-mistakes.md № 16, 23).

## Перед началом
1. Сборку ведёт один тред — он назван в треде «Архитектура и план разработки» строкой «Общую сборку ведёт …». Нет такой строки — написать её и только потом начинать; есть другая — не начинать. После перерыва (лимит сессии, «Продолжай») — сначала проверить, не взял ли сборку другой тред.
2. Список веток и порядок слияния — в описании PR: сначала ветки с миграциями, потом остальные.
3. **Один `spec:sync` на этап** (решение заказчика 15.11.2026, docs/decisions.md п. О-56): до сборки — отдельным PR со всеми версиями прототипа потоков этапа сразу (скилл `spec-sync`); его новости, которых ещё нет в продукте, ждут в `NEWS_NOT_YET` до этой сборки.

## Сборка
4. Ветка от свежего main; каждую ветку — `git merge --no-ff origin/<ветка>` (не rebase), конфликты — оставить обе строки в общих списках (CLAUDE.md).
5. **После каждого слияния** — проверить, что ветка пришла целиком: `git diff origin/<ветка> HEAD -- <файлы ветки>` показывает только чужие добавления, ничего из её строк не пропало; новые экспорты её помощников на месте.
6. **Миграции** — номера меняются один раз, после слияния всех веток, по порядку (скилл `db-migration`, «Миграции по очереди»); ссылки на прежние номера в `docs/` и комментариях — поправить.
7. **Старые строки.** Ветка поменяла текст, шаблон или формат — `git grep -nF '<старая строка>'` по всей сборке: тесты другой ветки могли сверять старую.
8. **Заглушки соседей** (№ 40). Найти места, где ветка ставила заглушку на месте функции другого потока (`git diff origin/main...origin/<ветка>` — `null`, `TODO`, «заглушка», «до слияния потока»), заменить настоящим вызовом и проверить тесты, которые на заглушку опирались: в сборке экран уже другой.
9. **Пункты docs** — `docs/decisions.md`, `docs/deviations.md`, `docs/acceptance-map.md`: оба пункта при конфликте, номера потоков не менять.

## Проверка
10. `pnpm check` один раз — в нём и типы `e2e/`, и загрузка сквозных тестов: пропавший помощник видно здесь, а не через полчаса на машинах CI.
11. Агенты-ревьюеры смотрят **стыки** веток (общие файлы, общие списки, чужие тесты, которые задевает каждая ветка), а не каждую ветку заново: в задании им — список веток и что каждая меняет.
12. Красный CI — скилл `ci-red`: исправить всё, что нашёл прогон, вместе с «не запускалось» и «со второй попытки», одним пушем.
13. Описание PR — скилл `pr-body`.

## После слияния — переход этапа
14. PR потоков, вошедшие в сборку, закрыть с комментарием «вошёл в общую сборку #N».
15. Были миграции — обновить `db/schema.json` в репозитории прототипа и залить в его main: постоянное разрешение заказчика 15.11.2026 (п. О-56), заново не спрашивать.
16. Каждому потоку — «этап N на стенде (main <SHA>), начинай этап N+1: <задача>, приёмка — <блок ТЗ>; сборку ведёт <тред>»; одна строка в тред «Общий план и статус задач». Порядок целиком — скилл аккаунта `stage-handoff`. Без этого сигнала потоки после своего «на стенде» ждут (пакет 14.11: 2,5 часа между этапами 2 и 3).

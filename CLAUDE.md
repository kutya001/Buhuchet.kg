# Buhuchet.kg — рабочий продукт

B2B SaaS для бухгалтерских аутсорсинговых организаций Кыргызстана. Организация ведёт 100+ контрагентов, у каждого 3–6 налоговых отчётов: это 4 000–8 000 отчётов в год.
Главное для пользователя: в любой момент видно, какой контрагент какой отчёт должен сдать, к какому сроку, сдан ли он и сколько по нему платить.
Система сама напоминает о сроках в Telegram. Каждый контрагент закреплён за сотрудником, который отвечает за его отчёты.
Каждая организация видит только свои данные; права — роли и 39 прав с областью «Свои / Все контрагенты».
Первый выпуск — весь прототип v57 на 100 %, без урезанного MVP; пилот — фирма заказчика (Кутман).

## Источник истины
- `spec/ТЗ Buhuchet.kg.md` — раздел модуля: правила и пункты приёмки «Как проверить, что всё работает».
- `spec/prototype/src/js/modules/<модуль>.js`, `spec/prototype/src/js/core/*.js` — логика и эталонные ответы; `spec/prototype/src/js/ui`, `spec/prototype/src/css` — как выглядит.
- `spec/data/*.json` — refDB (справочники платформы), gkedDB (ГКЭД), demoDB (демо-организация): черновик модели данных и начальное наполнение.
- `spec/` не правится руками: только `pnpm spec:sync` (хук запрещает).
- **На любой вопрос — как в прототипе** (решение заказчика 31.10.2026: прототип согласован на 100 %, `docs/decisions.md` п. О-2): ТЗ молчит, ТЗ или задача (Issue, план «Этап 2 — задачи») расходятся с прототипом, правило неясно — делать как в прототипе и ответа не ждать; прототип этого не показывает (серверное) — по ТЗ, молчат оба — по рекомендации. Защита (вход, сеансы, пределы, права и область, изоляция организаций, страница контрагента по ссылке, файлы, секреты) — по более строгому из ТЗ и прототипа. Каждое такое место — в `docs/deviations.md` (скилл `spec-deviation`).
- Уже сделанное до 31.10.2026 не как в прототипе пока остаётся как есть; их список — отдельным отчётом, когда заказчик попросит.
- Заказчику — только очень критичный вопрос, который может решить только он: пуш-уведомлением (скилл `spec-deviation`, п. 4).
- Архитектура и решения — `docs/architecture.md`, `docs/decisions.md`; план разработки ведёт тред «Архитектура и план разработки».

## Команды
- `pnpm setup:local` — PostgreSQL и MinIO в Docker, миграции, наполнение, корзина (нужен `.env`: `cp .env.example .env`).
- `pnpm dev` — сайт на http://localhost:3000 (API — /api, «здоровье» — /health).
- `pnpm check` — типы, линтер, переносимость, карта приёмки, все тесты. **Готово только когда он зелёный.**
- `pnpm test`, `pnpm test:coverage` (порог 80 % для domain и api), `pnpm test:e2e` (против запущенного сайта, `E2E_BASE_URL`).
- `pnpm db:generate` (миграция из схемы), `pnpm db:migrate`, `pnpm db:seed [--update]`.
- `pnpm db:create-org --name … --inn … --owner-fio … --owner-login …` и `pnpm db:create-admin --login …` — организация с владельцем и администратор платформы с временным паролем (до Админки).
- `pnpm check:portability`, `pnpm check:acceptance`, `pnpm format`.
- Как на VPS: `docker compose --profile app up -d --build --wait`.

## Устройство
- `apps/web` — Next.js (App Router), только интерфейс; API подключён одним catch-all роутом.
- `apps/worker` — фоновый исполнитель для VPS (на Vercel не запускается).
- `packages/api` — Hono + @hono/zod-openapi, маршруты по модулям; `packages/domain` — бизнес-правила без базы и сети (больше всего тестов);
  `packages/db` — Drizzle, SQL-миграции, RLS, наполнение; `packages/adapters` — переходники; `packages/shared` — схемы Zod; `packages/ui` — общие компоненты.
- Внутри пакетов код раскладывается по модулям ТЗ: `auth`, `org`, `staff`, `roles`, `contractors`, `reports`, `tasks`, `money`, `fees`, `finance`, `projects`, `kpi`, `files`, `kb`, `news`, `telegram`, `platform-dicts`, `admin`.
- У пакетов свои короткие CLAUDE.md — читать перед работой в пакете.

## Переносимость («своя мебель») — проверяется `pnpm check:portability`
- `@supabase/*` и `@vercel/*` — только в `packages/adapters`. Supabase для нас — обычный PostgreSQL и S3, Vercel — запуск Node.js и вызов расписания.
- В SQL нельзя: `auth.uid()`, `auth.jwt()`, схема `storage`, Realtime, pg_cron, pg_net. Расширения — только pg_trgm, pgcrypto, citext.
- Нельзя: Edge Runtime, Server Actions для данных, прямые запросы к базе из компонентов.
- Приложение не пишет на свой диск: файлы — только через `storage` (S3).
- Настройки — только из окружения через `loadConfig` (`packages/adapters/src/config.ts`); адресов и ключей в коде нет. Новая переменная — в схему config и в `.env.example`.

## Данные
- В каждой таблице организации — `org_id`, RLS-политика `orgIsolation` и тест «чужая организация не видна» в той же правке.
- Запросы к данным организаций — только в `withOrgContext` (задаёт `app.org_id`, `app.user_id`).
- Деньги — целые тыйыны (`bigint`), на экране «1 250,50»; сроки — `date` по Бишкеку (UTC+6); моменты — `timestamptz`.
- Изменение важных данных пишется в историю в той же транзакции; у записей — `version`, устаревшее сохранение → «запись изменена другим пользователем».
- Задачи по расписанию безопасны при повторе (уникальные ключи, досоздают только недостающее).

## Интерфейс
- Всё как в прототипе. Граница ПК и телефона — 768 px; на телефоне нижняя панель ровно из 4 модулей и «≡ Другие модули»; у карточек «На весь экран».

## Как работаем
- Одна задача (Issue) = одна ветка от свежего main = один PR. Порядок работы — скилл `module-from-spec`; миграции — `db-migration`; методы API — `api-endpoint`; экраны — `ui-screen`.
- В main напрямую не пушим. PR сливается сам (squash), когда зелёные все проверки: `check`, `docker-e2e`, `pr-policy`. Метка `hold` останавливает автослияние.
- PR, который меняет `.github/`, хуки `.claude/hooks/`, `.claude/settings.json` или скрипты слияния (`scripts/automerge.mjs`, `check-pr-policy.mjs`, `check-protected.mjs`, `protected-paths.mjs`), сам не сливается — сливает заказчик. Такие правки — отдельным PR, не вместе с работой модуля.
- Перед PR обязательно запустить агентов `spec-reviewer` и `security-reviewer` и вставить их выводы в раздел «Отчёт ревьюеров» описания PR (без него `pr-policy` красный). Человека-разработчика нет — их проверка обязательна.
- Миграции попадают в main по одной: если обе линии меняют базу, их PR сливаются один за другим — порядок в скилле `db-migration`.
- «Готово» значит: `pnpm check` зелёный; есть тесты на правила из ТЗ; каждый пункт приёмки — сквозной тест в `docs/acceptance-map.md`; экран совпадает с прототипом на ПК и телефоне; расхождения с ТЗ записаны в `docs/deviations.md`.
- Коммиты и описания PR — по-русски, коротко: что и зачем. Имена в коде — по-английски, комментарии — по-русски.
- Секреты (ключи Supabase, S3, токен бота) — только в настройках окружения Vercel, GitHub и облачной среды; никогда в коде, чате и репозитории.
- Рабочую базу и рабочий сайт Claude Code не трогает: миграции и выпуск — только GitHub Actions; на рабочий сайт версия выходит по команде заказчика «выпускай».

## Две линии (этап 2)
- Задачи этапа 2 идут двумя линиями (решение заказчика 30.10.2026): одновременно не больше двух задач, по одной в линии, порядок задач в линии постоянный — раздел «Путь в две линии» плана «Этап 2 — задачи» (`docs/` репозитория прототипа kutya001/DevBuhUchet.kg, ведёт тред «Архитектура и план разработки») и «Общий план и статус задач» (ведёт одноимённый тред). У Issues остаются метки «поток А» … «поток Е»: задачу делает тред потока-владельца модуля.
  - Одна задача = одно Issue = один PR от свежего main. Следующая задача линии начинается сразу после слияния предыдущей, без ожидания команды; ждать не опросом — подписаться на PR, которого ждёшь. Чужие задачи и задачи вне очереди без договорённости не берём.
  - Проверки — по одному разу: во время работы — тесты своего модуля; перед PR — один раз `pnpm check`; сквозные тесты — только в CI (`docker-e2e`), локально их не гоняем (сверка экрана с прототипом снимками остаётся локальной — это не сквозной тест); `spec-reviewer` и `security-reviewer` — по одному проходу, повторный — только если нашли критичное. После слияния в main CI заново не запускается, main целиком проверяет ночной прогон.
  - Вопросов заказчику по ходу работы нет: на любой вопрос — как в прототипе («Источник истины»); очень критичный — пуш-уведомлением, а работа тем временем идёт как в прототипе (защита — по более строгому варианту).
  - После каждого слитого PR, ответа заказчика или нового вопроса — одна строка в тред «Общий план и статус задач».
- Свои папки: поток правит код своих модулей — `packages/<пакет>/src/<модуль>`, `apps/web/src/<модуль>`, `packages/db/src/schema/<модуль>.ts`. Общее (`packages/ui`, общий список, оболочка, шкалы статусов, история) — только небольшими добавлениями; переделка общего — отдельным PR, о нём сообщить в тред плана, чтобы другая линия обновила ветку. `withOrgContext` и функции контекста RLS (`app.current_org_id()`, `app.current_user_id()`) — ключ изоляции организаций: любые их правки — только отдельным PR с сообщением в тред плана.
- Общие файлы-списки — одна строка на модуль, по порядку модулей ТЗ, не в конец: маршруты в `packages/api/src/app.ts`, экспорт `schema/index.ts`, словарь `l10n/texts.ts`, модули оболочки, `HISTORY_ENTITIES` и `HISTORY_ACTIONS`, шкалы статусов. При конфликте оставить обе строки.
- Тексты словаря — в своём `packages/domain/src/l10n/<модуль>-texts.ts`; демо-данные — в `packages/db/src/seed/demo-<модуль>.ts`, в `demo.ts` только вызов.
- Пункты `docs/decisions.md` и `docs/deviations.md` — в конец, номер с буквой потока задачи (кириллицей, по метке Issue «поток X»; задачи потока Е — «Е-1», какая бы сессия их ни вела; работа вне потоков — общие правила, общие задачи, просьбы заказчика без Issue потока — «О-1»): «А-1», «А-2»… Счёт у каждого потока свой, отдельно в decisions и в deviations; следующий номер — после наибольшего номера своего потока в main и в своих открытых PR. Заголовок — «## А-1. …» в deviations и «А-1. **…**» в decisions (перед ним пустая строка), ссылка — «docs/deviations.md п. А-1», в коде — `// ОТКЛОНЕНИЕ: docs/deviations.md#А-1`. Номер после слияния не меняется — на него сразу ссылаются в отчёте заказчику, в коде и в acceptance-map. При конфликте оставить оба пункта. Пункты с простыми номерами, слитые в main до этого правила, номера сохраняют; пункт с простым номером, ещё не слитый, получает номер своего потока, ссылки правятся в том же PR, а если вопрос заказчику уже задан с прежним номером — новый номер сообщить одной строкой в своём треде. В `docs/acceptance-map.md` — свой раздел «## Этап 2. <задача>» в конце. Расхождения записывает скиллом `spec-deviation` каждый поток сам.
- `pnpm spec:sync` — только отдельным PR без другой работы; другая линия потом обновляет ветку.
- Ветку обновлять с main слиянием (`git fetch origin main && git merge origin/main`, не rebase: после rebase нужен force-push, а он запрещён) — при сообщении автослияния «ветка отстала» и когда другая линия слила миграцию раньше.
- Правило стыков: если задача добавляет кусок на экран другой задачи, которого ещё нет, — делает кусок (компонент, метод API, тест) и не показывает его на экране, подключает его задача экрана; экран уже есть — подключает сама. Скрытый — только на экране: метод API доступен по сети сразу, поэтому у него с первого дня проверка входа, право из 39 с областью, ответ по схеме, 400 на неверные данные и тесты. Пункт приёмки, которому нужны обе задачи, закрывает слитая позже и записывает это в `docs/acceptance-map.md`.

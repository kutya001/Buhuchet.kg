# packages/api — API на Hono

- Не зависит от Next.js: в веб-приложении монтируется одним catch-all роутом `apps/web/app/api/[[...route]]/route.ts`, на VPS может работать отдельно (`src/standalone.ts`, @hono/node-server).
- Входы пакета: `@buhuchet/api/web` — обработчик для сайта (приложение API целиком), `@buhuchet/api/runtime` — зависимости из окружения, `@buhuchet/api/jobs` — `runDueJobs` для worker. Worker собирается в один файл и не должен импортировать приложение API (`createApp`, `src/web.ts`): в нём нативный модуль argon2, который в такой файл не собирается.
- Каждый метод — `createRoute` из `@hono/zod-openapi` со схемами Zod из `@buhuchet/shared` для входа и выхода; описание OpenAPI строится само: `/api/openapi.json`.
- Маршруты раскладываются по модулям ТЗ: `src/modules/<модуль>/…`; модуль экспортирует функцию, которая регистрирует свои маршруты (пример — `src/modules/system`).
- Зависимости (база, хранилище, часы, журнал, Telegram, настройки) приходят через `ApiDeps` (`src/deps.ts`); в тестах — поддельные (`src/testing.ts`). `process.env` здесь не читается — только `loadConfig` в `src/runtime.ts`.
- Общий слой (`src/middleware/`, подключён в `app.ts` для всех путей): `originCheck` — изменяющий запрос (всё, кроме GET, HEAD, OPTIONS) только с Origin нашего адреса (`APP_BASE_URL` или Host); `sessionGuard` — cookie → сеанс → организация: без сеанса 401, блокировка — 403 и сеанс закрывается, с временным паролем — только `/api/auth/me` и `/api/auth/password`; права сотрудника лежат в `c.var.access`, сеанс — в `c.var.session`. Открытые пути (без входа) перечислены в `PUBLIC_PATHS` (`middleware/session.ts`) — новый открытый метод добавляется туда явно; без Origin принимаются только `/api/cron/*` и вебхук Telegram — у них свой секрет в заголовке.
- Право метода — `middleware: [requirePermission('<право>')] as const` в `createRoute` (403 `forbidden`); метод для любого сотрудника — `requireEmployee`; метод Админки — `requirePlatformAdmin`. Область «Свои / Все контрагенты» — `scopeOf(c.var.access.subject, '<группа>')`, условие — в запрос.
- Данные организаций — только через `withOrgContext(deps.db, orgContextOf(c), …)` из `@buhuchet/db` (RLS): организация и автор берутся из сеанса, никогда из тела или параметров запроса; без организации в сеансе `orgContextOf` отвечает 403. Внутри открытой транзакции к базе — только через `tx`: запрос к пулу (`deps.db`) оттуда ждёт свободное соединение, а все они могут быть заняты такими же транзакциями — сайт зависнет (docs/decisions.md п. О-46); функция, которую зовут из транзакции, получает `tx`. Исключение — `serverTexts(deps)`: у словаря своё соединение (`deps.textsDb`).
- Тело запроса — не больше 1 МиБ (`bodyLimit` в `app.ts`); файлы идут в хранилище по подписанной ссылке, мимо API. Исключение — логотип организации (до 2 МБ, `OWN_BODY_LIMIT_PATHS`): метод сам ставит предел и проверяет, что это PNG или JPG, до сохранения; так же — файл «Ввода из Excel» показателей (до 4 МБ, `KPI_IMPORT_UPLOAD_PATHS`), его разбирает `src/lists/xlsx-read.ts` и нигде не хранит.
- Вход, выход, «кто я», смена пароля, «Забыли пароль?» — модуль `src/modules/auth`; таблицы входа читаются только функциями `app.auth_*` из `@buhuchet/db` (до выбора организации RLS их не показывает). Вход для неизвестного логина и неверного пароля отвечает одинаково («Неверный логин или пароль», пароль неизвестного логина сверяется с подставным хешем), «вход закрыт» наступает одинаково для любого логина, о блокировке сотрудника и организации — только после верного пароля; «Забыли пароль?» для любого логина отвечает одинаково и не быстрее `deps.resetResponseFloorMs` (в тестах 0). Не добавлять в эти методы ответов, по которым видно, есть ли логин (docs/deviations.md, п. 4).
- Telegram — модуль `src/modules/telegram`: ссылка привязки, отвязка, вебхук (секрет проверяет `webhookGuard` до разбора тела; адрес вебхука сайт сообщает Telegram сам — задача `telegram.register-webhook` из `jobsFor(config)`). Сообщение пользователю сразу, мимо очереди, — `sendNow`, текст — `botText(deps, '<ключ шаблона>', значения)` (шаблон справочника платформы, иначе `TELEGRAM_TEMPLATE_DEFAULTS`); о каждой смене пароля — `notifyPasswordChanged`, о замене и отвязке Telegram — в прежний чат. Другой чат вместо прежнего (привязанного или отвязанного последним) — только кодом из прежнего чата (`askRelinkCode` и `confirmRelink` в `webhook.ts`, docs/deviations.md п. О-20). Код и пароль в журнал не пишутся; ошибка Telegram метод не роняет. Очередь напоминаний — поток Б.
- Основа бота (поток Т, задача Т1; docs/decisions.md п. Т-1): сообщение с таблицами и кнопками — описание `BotMessage` из `@buhuchet/domain`; сразу — `sendBotMessage(deps, { userId, chatId }, message, kind, purpose)` (`bot.ts`), через очередь — `queueEvents` со строкой `{ …, text: botPlainText(message), message }`. Вид (таблицы или простой текст) выбирается при отправке, кнопки — в обоих. Нажатие кнопки принимает `handleBotPress` (`press.ts`): данные нажатия ничего не разрешают сами — сообщение ищется в журнале отправок по чату и номеру, кнопка сверяется с сохранённым описанием, чат — с привязкой; ядро проверяет ещё блокировки, временный пароль, «Действия из Telegram» организации (у действий с `change: true`) и право действия (`permission` — право из 40). Новое действие — обработчик `BotAction` одной строкой в `BOT_ACTIONS` (`actions.ts`); область «Свои / Все контрагенты» по записи и условия действия проверяет сам обработчик в `ctx.asUser((tx, access) => …)`. Нажатие — одна транзакция получателя в его организации: строка сообщения блокируется, действие выполняется, кнопка гаснет, история помечается «через Telegram»; сбой откатывает всё, второе нажатие получает «Кнопка устарела». Свою транзакцию мимо `asUser` (`ctx.deps.db`) обработчик не открывает; `RecordChangedError` и `RecordNotFoundError` — «Кнопка устарела». Из чата — только обратимые действия, деньги и удаление остаются на сайте. Тесты: свои действия — `deps.botActions`, нажатие — `telegramPress` (`src/testing.ts`), пример — `bot-press.test.ts`. Код подтверждения — `sendCodeMessage` (моноширинный код и кнопка «Скопировать код»); `POST /api/telegram/test` («Проверить бота», не чаще 10 в час), `PUT /api/telegram/plain` («Сообщения простым текстом»), `PUT /api/admin/telegram/bot/view` («Сообщения с таблицами» платформы).
- Действия сотрудника из чата бота (поток Т, задача Т2; docs/decisions.md п. Т-2, docs/deviations.md п. Т-5): обработчики — `src/modules/telegram/staff-actions.ts` (`STAFF_BOT_HANDLERS`: отчёт «В работе» и «Сдан», задача «Взять в работу» и «Выполнена», «Подтвердить» и «Вернуть»), вид сообщений о событиях сайта с кнопками — `staff-view.ts` (`taskView`, `fixView`, `botSiteUrl` — ссылка «Открыть» только у сайта по https), сообщения с кнопками следом за напоминанием — `reminders.ts`. «Ответ боту»: обработчик нажатия возвращает `ask` (что прислать: `file` или `text`) — ядро отправляет сообщение-просьбу с «Отменой»; ответ (файл, фото, текст — ответом на сообщение или просто в чат, тогда к последней открытой просьбе за сегодня) принимает `handleBotReply` (`reply.ts`) и вызывает `reply(ctx, { text } | { file, note })` действия из просьбы — с теми же проверками ядра и в той же транзакции получателя, что нажатие. Не тот ответ просьбу не закрывает. Ответ на закрытую или вчерашнюю просьбу другой открытой не достаётся; одно сообщение человека принимается один раз (`BOT_REPLY_ONCE` по номеру сообщения — повтор доставки от Telegram); текст с «/» — не ответ. Файл из Telegram скачивается до транзакции (право действия проверяется до скачивания) и прикрепляется `attachStoredFile`. В своём обработчике отказывать по каждому действию: чужая организация, область «Свои», право — с тестом (пример — «чужая организация, область „Свои“ и право проверяются у каждого действия» в `staff-bot.test.ts`). Пределы: `BOT_REPLY_RATE_LIMIT`, `BOT_PRESS_RATE_LIMIT`. Тесты: сообщение боту — `telegramUpdate(text, chatId, { replyTo, document, photo, caption })`, файлы подставного бота — `tg.files`; пример — `staff-bot.test.ts`.
- Таблицы в сообщениях бота (поток Т, задача Т3; docs/decisions.md п. Т-3, docs/deviations.md п. Т-6): сообщение дня с отчётами — `BotMessage` с таблицами по разделам и своим простым текстом `plain` (прежние строки), не собралось — уходит прежний текст (`reminders.ts`, строка таблицы — `botReportRow` в `staff-view.ts`); по понедельникам владельцу и главному бухгалтеру — отдельное сообщение «Сводка недели» (ключ `reminders:<пользователь>:<день>:week`) с таблицей по сотрудникам, кнопками «Напомнить» и разделом «Долги за обслуживание» с кнопками «Скопировать напоминание» (долги — только при функции и праве «Видеть плату за обслуживание», по области группы «Контрагенты» получателя). «Напомнить» — действие `nudge` (`staff-nudge.ts`): право «Просматривать отчёты» и область «Все» отчётов, сотрудник — действующий из той же организации, раз в день на сотрудника (ключ очереди `nudge:<пользователь>:<день>`), данных не меняет. Действие, которое данных не меняет, но что-то отправляет, ставит `limited: true` (входит в `BOT_PRESS_RATE_LIMIT`) и возвращает номера поставленных в очередь сообщений в `queued` — ядро отправит их сразу после транзакции нажатия. Тексты в обработчике — только `ctx.text` (шаблон бота) и `ctx.tr` (словарь): ядро читает их до транзакции (`botPressTexts`); `botText` и `messageTemplates` внутри `asUser` — только с `tx` (п. О-46), как `fixView` и `taskView` (`staff-view.ts`). Тесты — `staff-tables.test.ts`.
- «Это не я» под сообщениями бота о безопасности (поток Т, задача Т4; docs/decisions.md п. Т-4, docs/deviations.md п. Т-7): «Пароль изменён», «Привязан другой Telegram» и «Telegram отвязан» отправляет `sendSecurityNotice(deps, { userId, chatId, shared, orgName }, notice, values, purpose)` (`bot.ts`) — с кнопкой «Это не я» (`securityBotMessage` домена; в данных кнопки — вид сообщения и момент отправки, срок — `NOT_ME_HOURS`); после сброса пароля владельцем сообщение идёт без кнопки. Нажатие — действие `notMe` (`security-actions.ts`) с `security: true`: ядро не требует, чтобы чат был ещё привязан, и не смотрит на «Действия из Telegram», блокировки отказывают («Нет права»). После сброса пароля владельцем или администратором платформы прежнему чату бот не доверяет: кнопки, выданные до сброса, погашены, а пока пароль временный или действует разрешение привязать Telegram без кода (и под сообщением о привязке по такому разрешению — `{ inert: true }`), кнопка только отвечает, что делать (`telegram.notme.after_reset`). Вход закрыли, пока проверялся пароль, — `openSession` возвращает null, вход отвечает 403. Всё делает одна функция базы от имени получателя (`telegramNotMe`): сеансы завершены, чужая привязка снята, вход закрыт (кроме администратора платформы) до нового пароля от владельца или администратора; владельцам — сообщение сразу, администраторам платформы — через очередь. Вход с верным паролем при закрытом входе — 403 `account_locked` с `details.variant` `not_me` или `not_me_owner` (`auth-errors.ts`). Новое сообщение о безопасности — строка в `SECURITY_NOTICE_DEFS` домена и вид журнала в условии `app.telegram_not_me`. Тесты — `security.test.ts`.
- Меню команд бота (поток Т, задача Т5; docs/decisions.md п. Т-5, docs/deviations.md п. Т-9): команду («/today», «/week», «/overdue», «/find» или подпись кнопки меню) вебхук принимает раньше «ответа боту» — `handleBotCommand(deps, { chatId, fromId, messageId, reply, text })` (`reply` — сообщение прислано ответом на другое: тогда подпись кнопки — не команда) (`commands.ts`): личный чат и его хозяин, предел частоты нажатий, одно сообщение — один раз; чат без привязки — подсказка `tgStart` без кнопок меню; ответ — по каждому логину чата (`botChatUsers`) в `withOrgContext` от его имени: блокировки, временный пароль, разрешение без кода, администратор платформы, выключенный модуль Telegram или нет права команды — «Нет права». Команды ничего не меняют и работают при выключенных «Действиях из Telegram». Ответы собирает `command-view.ts` (`reportsCommandMessage`, `contractorCardMessage`, `findContractorAnswer`; налоги к оплате — только с модулем «Оплата налогов», отчёты карточки — с `repView`, долг — с модулем и правом `fee`); «Найти контрагента» — просьба бота `cpFind` и кнопка `cpCard` (`command-actions.ts`, действия ядра с `limited`). Действие-ответ может прислать новое сообщение — `BotReplyResult.send`. Кнопки под полем ввода — `sendBotMessage(..., { menu })` и `botMenu(deps)`; другой текст в привязанном чате — `sendBotHint`. Меню Telegram сообщает задача `telegram.register-webhook` (`botMenuCommands`). Новая команда — строка в `BOT_COMMANDS` домена, ветка ответа в `command-view.ts` и тест. Тесты — `commands.test.ts`.
- Темы в чате с ботом (поток Т, задача Т7; docs/decisions.md п. Т-7, docs/deviations.md п. Т-11): любая отправка в Telegram идёт через `sendInTopic(deps, chatId, { kind, orgId?, userId? }, (threadId) => …)` (`topics.ts`) — тема по виду журнала (`botTopicOf` домена), создаётся при первом сообщении, удалённая — заново; переключатель выключен, темы не включены в @BotFather или вида без темы — `threadId` пустой. В параметры отправки номер темы — `threadOption(threadId)`. Разбор нажатия и сообщения человека вебхук оборачивает в `inReplyThread` — ответы в этот чат идут в ту же тему; организация темы, где написали, — `replyTopicOrg`. Новый путь отправки мимо `sendNow`, `sendBotMessage` и очереди — тоже через `sendInTopic`. Переключатель — `PUT /api/admin/telegram/bot/topics`, состояние @BotFather — `topicsReady` в `GET /api/admin/telegram/bot`. Тесты — `topics.test.ts` (подставной бот: `tg.topics`, `tg.topicsOn`, `tg.deleteTopic`; сообщение в теме — `telegramUpdate(text, chat, { threadId })`).

- Ошибки — `{ error: { code, message } }`; `code` — ключ словаря интерфейса. Запрос к базе дольше предела вида работы общий обработчик отвечает 503 `query_timeout` (у методов списка — в `listQueryResponses`). `RecordChangedError` и `RecordNotFoundError` из `@buhuchet/domain` метод не ловит: общий обработчик отвечает 409 `record_changed` («Запись изменена другим пользователем», в `details.version` — текущая версия) и 404 `not_found`. Метод, который сохраняет запись с версией, добавляет в ответы `...versionedSaveResponses` (`src/errors.ts`). Ошибку в журнал — только под ключом `err` (`logger.error({ err }, …)`): так из ошибок запросов к базе вычищаются значения параметров.
- Сотрудники — модуль `src/modules/staff`, роли и справочник прав — `src/modules/roles` (право «Сотрудники и роли», список и карточка сотрудников — «Просматривать сотрудников»). Правила ролей не пишутся в обработчике: `staffActionRefusal`, `newEmployeeRoleRefusal`, `roleChangeProblem`, `roleDeleteRefusal`, `copiedRolePermissions` из `@buhuchet/domain` (актор — `staffActor(c)`: его права и область для «не выдаёт больше своего») — те же, что у формы роли (docs/deviations.md, п. 15). Отказ по правилу внутри транзакции — `apiFail(статус, код, текст)` из `src/errors.ts`: транзакция откатывается, отвечает общий обработчик; статус — из описания маршрута.
- «Локализация» — модуль `src/modules/l10n`: `GET /api/l10n` без входа, тексты `ui_texts` поверх `UI_TEXTS`, кэш в памяти, сверка с отметкой базы (`uiTextsStamp`) не чаще раза в секунду, ETag и 304; база недоступна — тексты по умолчанию без кэша.

# packages/db — схема, миграции, RLS, наполнение

## Миграции
- Схема таблиц — в `src/schema/*.ts` (Drizzle). После правки схемы: `pnpm db:generate` → в `migrations/` появляется SQL-файл; его читаем глазами и коммитим вместе со схемой.
- То, что Drizzle не генерирует (функции, роли, права, триггеры, особые индексы), — отдельной миграцией: `pnpm --filter @buhuchet/db exec drizzle-kit generate --custom --name=<что_делает>`, SQL пишем руками.
- Применённые миграции (уже в main) не правятся никогда — только новая миграция поверх. Хук запрещает их менять.
- `drizzle-kit push` запрещён. Миграции применяет `pnpm db:migrate`: локально и в CI — к своему PostgreSQL, на стенде и рабочем сайте — GitHub Actions при выпуске.
- Миграции попадают в main по одной: очередь держит открытый PR с меткой «миграция» (один на репозиторий). Номер миграции окончательный только после слияния; перед слиянием свои новые миграции пересоздаются после тех, что уже в main (скилл `db-migration`, «Очередь миграций»).
- Схема своего модуля — свой файл `src/schema/<модуль>.ts`, в `schema/index.ts` — одна строка экспорта по порядку модулей ТЗ; демо-данные — `src/seed/demo-<модуль>.ts`, в `demo.ts` только вызов.
- Расширения — только pg_trgm, pgcrypto, citext. Функции Supabase (`auth.uid()`, `auth.jwt()`, схема `storage`), pg_cron, Realtime — нельзя (`pnpm check:portability`).

## Организации и RLS
- Каждая таблица с данными организации: столбец `org_id uuid not null references organizations(id)`, `.enableRLS()` и политика `orgIsolation(t.orgId)` из `src/schema/rls.ts`.
- API в начале транзакции задаёт `app.org_id` и `app.user_id` (`withOrgContext`); политики сравнивают с `app.current_org_id()`.
- Там же — предел времени запросов по виду работы (`kind`: `request` 15 с по умолчанию, `export` 60 с, `job` 4 мин; `QUERY_TIMEOUT_MS`, docs/decisions.md, п. 38); у `withUserContext` — четвёртый параметр. Запрос дольше предела — `queryTimedOut(err)` из `src/errors.ts`.
- Приложение подключается ролью из `DATABASE_URL` — член `buhuchet_app` без права обходить RLS; владелец таблиц (`DATABASE_ADMIN_URL`) — только миграции и наполнение.
- В той же правке, что и таблица, — тест «чужая организация не видна» (пример — `src/rls.test.ts`).

## Данные
- Деньги — `bigint` тыйынов (`money()` из `src/schema/columns.ts`), даты сроков — `date` (строка `YYYY-MM-DD`), моменты — `timestamptz`.
- У изменяемых записей — `version integer` (защита от одновременной правки) и `created_at`/`updated_at`.
- История изменений (`audit_log`) пишется в той же транзакции, что и изменение (`src/history.ts`):
  - правка записи с версией — `updateWithHistory(tx, { table, entity, id, version, patch })`: блокирует запись, при устаревшей версии бросает `RecordChangedError` (чужая правка не затирается), иначе повышает `version`, ставит `updated_at`/`updated_by` и пишет «было → стало» по изменённым полям; правка без изменений ничего не пишет;
  - `patch` — только столбцы таблицы без служебных (иначе ошибка), собирается из явного списка полей формы; `key` — ключевой столбец, если он не `id` (учётная политика — `org_id`); `where` — условие области «Свои контрагенты» (вне области — «не найдена»); `changes` — изменения дочерних записей (права роли), которые тоже поднимают версию;
  - создание, удаление и прочие действия — `writeHistory(tx, { entity, entityId, action, changes?, reason? })`; сама запись при этом не меняется;
  - организация, автор и время ставит база из контекста `withOrgContext`, подменить их политика не даёт; без пользователя — «Система»; значения секретных полей (`isSecretField`: хеш пароля, `*Hash`, `*Token`, `*Secret`, плюс `secretFields`) не пишутся;
  - записи истории роль приложения не меняет и не удаляет (нет прав UPDATE и DELETE); новые виды записей и действия — в `HISTORY_ENTITIES` и `HISTORY_ACTIONS` из `@buhuchet/domain`.
- «История статусов» — своя таблица `status_history` (`src/status.ts`, docs/decisions.md, п. 33): смена статуса — `writeStatusChange(tx, { scale, entityId, from, to, reason?, rollback? })` в той же транзакции, что меняет статус записи; чтение — `readStatusHistory(tx, scale, entityId)` (сначала старые, автор — краткое ФИО или «Система»). Организация, автор и время — из контекста, записи только добавляются; коды статусов каждой шкалы проверяет ограничение `status_history_status_check` (из `STATUS_SCALE_DEFS` домена) — новый код статуса требует миграции.

## Наполнение
- `pnpm db:seed` — справочники платформы из `spec/data/refDB.json`, ГКЭД из `spec/data/gkedDB.json`, демо-организация из `spec/data/demoDB.json` (не на рабочем сайте). По умолчанию только добавляет недостающее; `--update` обновляет изменившиеся разделы (локально и на стенде после `pnpm spec:sync`).
- Модуль, у которого появляются таблицы, добавляет свой наполнитель демо-данных в `src/seed/demo-<модуль>.ts`, а в `src/seed/demo.ts` — только его вызов.
- Записи демо-организации получают постоянный uuid `demoId(<вид>, <код из demoDB.json>)`: наполнители ссылаются друг на друга, как записи прототипа (у контрагента `resp: 'e3'` → `demoId('employee', 'e3')`). Демо-сотрудники входят паролем `DEMO_PASSWORD`; `--update` с новым паролем меняет его и закрывает их сеансы.
- Администратор платформы из `PLATFORM_ADMIN_LOGIN` и `PLATFORM_ADMIN_PASSWORD` (`src/seed/admin.ts`): создаётся, если его нет, с временным паролем; уже созданного наполнение не трогает, логин сотрудника организации — ошибка.
- Словарь текстов интерфейса (`ui_texts`, общий, роль приложения только читает) наполняется из раздела `localization` refDB.json и `UI_TEXTS` (`@buhuchet/domain`); `--update` не трогает тексты, поправленные в Админке (`updated_by` задан). Прав на запись у роли приложения нет (миграция 0017); отметка `uiTextsStamp` (число текстов и хеш) меняется с любой правкой, даже прямо в таблице.
- Каталог прав (`permissions`) и шаблоны ролей (`role_templates`) наполняются из refDB; набор прав — `PERMISSIONS` в `@buhuchet/domain`, при расхождении наполнение останавливается.

## Справочники платформы для контрагентов и отчётов
- Свои таблицы с внешними ключами (`src/schema/platform-dicts.ts`, миграции 0022–0023, docs/decisions.md, п. 36): органы `authorities`, режимы `tax_regimes`, основания `report_bases`, УГНС `tax_offices`, виды отчётов `report_types` (+ связи `report_type_regimes` — «применяется» / «не применяется», `report_type_bases`), льготы и статусы `tax_benefits` (+ `tax_benefit_report_types` — добавляет / убирает, `tax_benefit_offices`, `tax_benefit_due_rules`), производственный календарь `production_calendar` (день `MM-DD` — праздник каждый год, `YYYY-MM-DD` — на дату; вид — праздник, перенос, рабочая суббота); с задачи 2.01 (миграции 0027–0028, docs/decisions.md, п. 39) — формы собственности `ownership_forms`, ставки единого налога `single_tax_rates` («Добавляется к ставкам» — массив кодов `adds_to`), причины изменения срока `due_change_reasons`. Мелкие разделы refDB.json остаются в `platform_reference`.
- Ключ — постоянный код из refDB.json (у видов отчётов — `id`, у УГНС — `id`, код ГНС — отдельное поле): ссылки и наполнение идут по нему, переименование не создаёт дубль. Значение не удаляется, а отключается (`active`); используемое значение удалить не даёт внешний ключ.
- Роль приложения только читает (RLS `platformReadOnly` и `REVOKE`, миграции 0023 и 0028). Наполнение — `seedPlatformDicts` (`src/seed/platform-dicts.ts`): схемы Zod строгие (новое поле refDB.json останавливает наполнение, пока для него нет столбца), ссылки на органы, режимы, основания и УГНС проверяются до записи; без `--update` добавляются только новые записи со своими связями, с `--update` изменившиеся обновляются (версия +1), поправленные в Админке (`updated_by` задан) и их связи не трогаются, лишние не удаляются (кроме дней календаря из наполнения: он сопоставляется по дате).
- Чтение — `src/platform-dicts.ts`: `listReportTypes`, `listTaxRegimes`, `listTaxBenefits`, `listReportBases`, `listTaxOffices`, `listAuthorities`, `listOwnershipForms`, `listSingleTaxRates`, `listDueChangeReasons` (по умолчанию только действующие, и отключённый вид отчёта не приходит в видах основания и в «добавляет» льготы; `{ all: true }` — все; порядок справочника; сверка с ГНС — не для организаций) и `productionCalendarEntries` (для `calendarYear` из `@buhuchet/domain`). Связи приходят массивами кодов из подзапросов: в подзапросе столбец внешней таблицы — через `outer(column)`, иначе drizzle пишет его без имени таблицы и он сравнивается со столбцом подзапроса.
- «Налоги и ставки» — пока раздел `platform_reference` (`src/taxes.ts`: `listTaxes`, своя таблица — с правкой в Админке, задача 2.36); `taxGkedNames` — названия кодов ГКЭД из связей налогов одним запросом.

## Справочники организации
- Виды отчётов организации — `org_report_types` (`src/schema/dicts.ts`, миграции 0029–0030, docs/decisions.md, п. 40): строка на вид каталога, который организация хоть раз подключала; отключение — `enabled = false`, строку не удаляют (у роли приложения нет DELETE). Функции — `src/dicts.ts`: настройки (`listOrgReportTypeSettings`, `getOrgReportTypeSetting`), подключение и правка с историей `org_report_type` (`createOrgReportType`, `updateOrgReportType`, `lockOrgReportTypes` для подключения нескольких в одной транзакции), список каталога глазами организации (`listOrgReportTypesPage`, `listOrgReportTypeValues`, `exportOrgReportTypes`): тексты сроков приходят готовыми строками из `@buhuchet/domain` и подставляются в запрос (`jsonb_to_recordset`).
- «Справочники платформы» глазами организации — `src/platform-values.ts` (docs/decisions.md, п. 41): плитки (`platformDictTiles`), окно справочника (`listPlatformDictPage`, `listPlatformDictValues`, `exportPlatformDict`) и «Поиск по всем значениям» (`listPlatformValuesPage`, `listPlatformValueValues`, `exportPlatformValues`). Строки собираются из таблиц справочников и разделов `platform_reference` и идут в общий механизм списков одним параметром (`jsonb_to_recordset`); у справочника без сортировки (статусы, шаблоны) — порядок по столбцу `n`. В тестах все справочники платформы наполняет `seedAllPlatformDictionaries` (`src/testing.ts`).
- «Попросить добавить» — `dict_change_requests` (`src/schema/dicts.ts`, миграции 0031–0032): `createDictRequest` (организация и автор — из контекста, история `dict_request`), `listDictRequests` («Мои запросы», последние 200). У роли приложения нет UPDATE и DELETE, а вставку только своим автором, со статусом «Новый» и без ответа пропускает ограничительная `dict_change_requests_insert_guard`; ответ даст Админка (её функция — SECURITY DEFINER). Плашка Админки — `app.admin_dict_requests()` в `adminOrgSummary`.

## Организации, пользователи, роли
- Новая организация — только через `createOrganization` (`src/organizations.ts`): роли из шаблонов, владелец, учётная политика в одной транзакции. Служебные команды: `pnpm db:create-org`, `pnpm db:create-admin`.
- Задача по расписанию берёт список организаций `orgIds(db)` (функция `app.org_ids()`) и работает с каждой в своей `withOrgContext`.
- Ссылки между записями организации — на пару `(id, org_id)` (составной внешний ключ), чтобы запись нельзя было связать с чужой организацией.
- Сотрудники — `src/staff.ts` (`listEmployeesPage` — страница списка, `getEmployee` — запись с `phoneText` по маске «Кодов телефонов», `createEmployee`, `lockEmployee`, `roleAccess` — роль для решения о сотруднике, строка блокируется FOR SHARE, `roleScopeMap`, `endUserSessions`, `phoneCodes`), роли — `src/roles.ts` (`listRoles`, `getRole`, `createRole`, `replaceRolePermissions`, `setRoleScopes`, `roleInUse`, `deleteRole`, `permissionCatalog`); всё — в `withOrgContext`, хеш пароля не читается. Новая запись получает организацию и автора из контекста (`app.current_org_id()`, `app.current_user_id()`).
- «Моя организация» — `src/org.ts` (`getOrgProfile`, `getOrgPolicy`, `orgFeatures`, `orgPolicyHistory`, `orgRoleOptions` — роли для «Роли по умолчанию»). У `organizations` роль приложения меняет только поля профиля и служебные поля правки (права на столбцы, миграция 0015); новое изменяемое поле организации — в `GRANT UPDATE (…)` новой миграцией.
- Нарушенное ограничение — `uniqueViolation(err)` и `foreignKeyViolation(err)` из `src/errors.ts` (имя ограничения): так метод отвечает «логин занят», «такая роль уже есть», а не 500.
- Частота действий — `rate_limits` (миграция 0026): `takeRateLimit(db, предел, субъект)` → можно (номер) / `busy` / `limited`, после действия — `releaseRateLimit(db, предел, субъект, номер)`; вызывать на `db`, не в транзакции модуля. Таблицу роль приложения не видит — только функции `app.rate_limit_*`; строки старше суток удаляет `cleanupRateLimits`.

## Списки
- Страница списка — `selectListPage` (`src/list.ts`): столбцы `ListColumns` (ключ — как у столбца экрана; `value` — выражение для фильтра, `sort` — своё выражение сортировки, `compact` — телефон без пробелов и скобок, `total` — сумма по фильтру, `display` — текст как на экране для поиска, подписи группы, значений фильтра и выгрузки, `label` — ключ словаря для заголовка в Excel), фильтры, поиск, сортировка и группировка — только по этим столбцам (иначе `ListQueryError` → 400); в `value` и `sort` — без параметров запроса (по ним группирует `group by`; постоянный текст — прямо в SQL, тексты словаря — только в `display`); область «Свои» — `scope`, всегда явно (`undefined` — вся организация), одна и та же у страницы, значений и выгрузки; число записей и итоги — оконными функциями в том же запросе, страница за концом — последняя. Поиск — `searchCondition` (эталон `matchesSearch` в `@buhuchet/domain`). Группировка (до двух уровней) — модуль даёт ещё `from` (те же таблицы с любыми полями, `ListFrom`): группы с числом записей и итогами — по запросу на уровень, подпись группы — `min(...)` (тексты словаря — параметры запроса, в `group by` их не повторить). Значения для фильтра-галочек — `selectListValues` (не больше `LIST_VALUES_LIMIT`, `total` — сколько всего, `q` — «Найти значение» по всем значениям, эталон `matchesValue`; фильтр-галочки с шагами `steps` — `case when` по шагам, эталон `enumChecked`), записи для Excel — `selectListExport` (не больше `EXPORT_ROWS_LIMIT`). Пример — `listEmployeesPage`, `listEmployeeValues`, `exportEmployees` в `src/staff.ts`.
- Текст сортируется естественно («Номер 2» перед «Номер 10»), без учёта регистра, пустые — в конце: правило сравнения `app.ru_natural` (ICU `ru-u-kn`, миграция 0019).
- Настройки вида списков — `view_settings` (миграция 0018): строка на пользователя и ключ списка, видит и меняет только сам пользователь (у администратора платформы `org_id` пустой); `listViewSettings`, `saveViewSettings`, `resetViewSettings` из `src/views.ts`. Истории и версии нет — последнее сохранение побеждает.

## Вход и сеансы
- Вход, проверка cookie и выход идут до того, как известна организация, поэтому `users` и `sessions` в это время читаются только функциями `app.auth_*` (миграции 0009 и 0013, SECURITY DEFINER, `search_path` задан, выполняет только `buhuchet_app`) через обёртки `src/auth.ts`: `findLogin`, `reserveLoginAttempt` (попытка по набранному логину занимается до проверки пароля), `clearLoginAttempts`, `startSession`, `sessionByToken`, `endSession`, `changeOwnPassword`.
- Неверные пароли считаются в `login_attempts` по набранному логину, есть он или нет (docs/deviations.md, п. 4, решение Б): таблица без организации, роль приложения её не видит и не меняет — только `app.auth_login_attempt`, `app.auth_login_clear`, `app.auth_login_cleanup`. Новый способ задать пароль тоже снимает счёт (`clearLoginAttempts` или как в `app.auth_reset_complete`). Обходить RLS чтением таблиц нельзя; новая такая функция — тоже узкая, с `REVOKE … FROM PUBLIC`.
- В таблице сеансов — только SHA-256 токена; токен знает лишь cookie.
- Telegram и «Забыли пароль?» (миграция 0011): привязка `telegram_links`, ссылки `telegram_link_tokens` (SHA-256 токена), коды `password_reset_codes` (хеш argon2id) — у всех `org_id` (пусто у администратора платформы) и RLS. Без входа и без организации они читаются и меняются функциями `app.telegram_*`, `app.auth_reset_*`, `app.admin_find_user` через обёртки `src/telegram.ts`; привязать, отвязать и задать пароль по коду можно только пользователю из `app.user_id` (API вызывает это в его `withOrgContext` и пишет историю в той же транзакции). Временный пароль владельцем — `setTemporaryPassword` в контексте организации (RLS).
- Файлы (миграции 0033 и 0034, docs/decisions.md, п. Г-1): `files` — одна таблица на все записи (`source_kind`, `source_id`, `contractor_id`), состояния `pending` → `ready` → `deleted`; обёртки — `src/files.ts`. Вставить можно только свою загрузку `pending`, удалённый файл не меняется, стереть строку — только у `pending` (ограничительные политики); менять можно только состояние, контрагента, комментарий и служебные поля (права на столбцы). `status_history.file_id` — ключ на файл своей организации; `readStatusHistory` отдаёт имя и `available`.
- Права и роль сотрудника для общего слоя API — `loadEmployeeAccess(tx, employeeId)` в `withOrgContext`; администратор платформы без организации — `withUserContext`.

## Тесты
- Тесты базы создают временную базу на сервере из `DATABASE_ADMIN_URL` (`createTestDatabase` из `src/testing.ts`), применяют миграции и удаляют базу в конце. Права и шаблоны ролей для `createOrganization` — `seedAccessReference(db)`. Справочники для контрагентов и отчётов — `seedPlatformDictionaries(db)`.
- Без `DATABASE_URL` и `DATABASE_ADMIN_URL` тесты базы пропускаются; в CI (`REQUIRE_INTEGRATION_TESTS=1`) — падают.

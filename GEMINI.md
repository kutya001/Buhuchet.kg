# GEMINI.md — Главные правила и гайдлайны для AI-агента (Antigravity)

Этот документ является главным управляющим файлом для AI-ассистента (Antigravity / Cursor / Windsurf). Все сгенерированные файлы, компоненты, серверные функции и структуры данных ОБЯЗАНЫ строго соответствовать изложенным ниже правилам.

---

## 1. ОСНОВНОЙ СТЕК ТЕХНОЛОГИЙ

- **Fullstack Framework:** Next.js (App Router, React Server Components, Server Actions).
- **Язык программирования:** TypeScript (строгий режим `strict: true`).
- **Стилизация и UI:** Tailwind CSS, Shadcn UI, Lucide Icons.
- **База данных и Аутентификация:** Supabase (PostgreSQL, Row Level Security - RLS, Supabase Auth).
- **Хранилище сканов и файлов:** Cloudflare R2 (подключение через `@aws-sdk/client-s3`).
- **Фоновые задачи и очереди:** Upstash QStash / Inngest (для асинхронных операций).
- **Интеграция с Telegram:** Telegram Webhooks (Next.js API Routes) + Aiogram / Node-telegram-bot-api.
- **Экспорт данных:** SheetJS (`xlsx`) на стороне клиента.

---

## 2. ЖЕСТКИЕ ПРАВИЛА НАПИСАНИЯ КОДА (CODE STYLE & STANDARDS)

### 2.1 Строгий TypeScript
- Запрещено использовать тип `any`. Для всех сущностей, ответов API, параметров Server Actions и пропсов UI-компонентов должны быть определены явные `interface` или `type`.
- Формы и входные данные API-маршрутов должны валидироваться через **Zod**.

### 2.2 Сжатие изображений на стороне клиента (Client-Side Compression)
- **Критическое правило:** Все изображения, фото накладных и сканы ДО отправки в облачное хранилище (Cloudflare R2) ДОЛЖНЫ быть сжаты в браузере с помощью библиотеки `browser-image-compression` (максимальная ширина — `1000px`, качество — `0.7`, целевой объем — до 200 КБ).
- Запрещено загружать несжатые исходники с мобильных устройств прямо на сервер.

### 2.3 Безопасность и секреты
- Секретные ключи (`SUPABASE_SERVICE_ROLE_KEY`, `R2_SECRET_ACCESS_KEY`, `TELEGRAM_BOT_TOKEN`) разрешено использовать строго на сервере (Server Actions, API Routes).
- Клиентские компоненты (`"use client"`) должны иметь доступ только к публичным переменным с префиксом `NEXT_PUBLIC_`.

### 2.4 Обработка ошибок
- Все серверные вызовы и запросы к БД оборачиваются в блок `try/catch`.
- Ответы сервера должны возвращать структурированный объект вида: `{ success: boolean, data?: T, error?: string }`.

---

## 3. АРХИТЕКТУРНЫЕ ОГРАНИЧЕНИЯ (ARCHITECTURE BOUNDARIES)

1. **Мультиарендность (Multi-Tenancy):** Каждая таблица в базе данных (кроме глобальных системных) ОБЯЗАНА содержать поле `company_id`.
2. **Row Level Security (RLS):** Все операции с базой данных должны учитывать `company_id` текущего авторизованного пользователя. Прямые манипуляции с данными чужих организаций недопустимы.
3. **Лимиты выполнения Vercel (10 сек):**
   - Генерация файлов Excel для 1С выполняется **на стороне клиента** (в браузере пользователя через `SheetJS`).
   - Долгие фоновые процессы (обработка фото, рассылки, сверки) выносятся в очереди (Upstash QStash).
4. **Telegram Webhooks:** Роут `/api/telegram-webhook` должен отдавать ответ `200 OK` Telegram-серверу быстрее чем за 2 секунды. Все тяжелые действия выполняются асинхронно в фоне.

---

## 4. РЕГЛАМЕНТ ХРАНЕНИЯ И АКТУАЛИЗАЦИИ БАЗЫ ДАННЫХ (`./DATABASE/`)

Вся физическая схема PostgreSQL, хранимые функции, RLS-политики, инкрементальные скрипты изменений и подробнейшая документация хранятся строго в локальной директории `./DATABASE/`.

### Обязательные требования к подпапкам и файлам:
1. **Сводный Воспроизводимый DDL Скрипт (`./DATABASE/schema.sql`):**
   - Полный чистый SQL-скрипт создания всей структуры PostgreSQL (таблицы, связи, индексы, RLS, триггеры, процедуры/функции) для разворачивания БД с нуля.
2. **Подробнейшая Документация БД (`./DATABASE/DATABASE_DOCUMENTATION.md`):**
   - Содержит детальное описание **каждой таблицы** (бизнес-назначение, задачи, роли) и **каждой колонки** (название, тип данных, NULL-constraints, бизнес-цель и связь).
3. **История Изменений Схемы (`./DATABASE/changes/`):**
   - Папка для сохранения всех отдельный скриптов миграций и изменений. Каждое изменение БД обязано сохраняться под именем `YYYY-MM-DD_short_description.sql`.

⚠️ **Правило актуализации:** При ЛЮБОМ изменении БД (создании таблиц, добавлении колонок, обновлении RLS) AI-агент ОБЯЗАН обновлять `./DATABASE/schema.sql`, добавлять точечный файл в `./DATABASE/changes/` и обновлять `./DATABASE/DATABASE_DOCUMENTATION.md`.

## 6. ОБЯЗАТЕЛЬНЫЙ ПРОЦЕСС ЗАВЕРШЕНИЯ ЗАДАЧ (DEFINITION OF DONE)

Каждый раз, когда ты (AI-агент) завершаешь разработку новой фичи, создаешь новый модуль, таблицу в БД или меняешь логику взаимодействия сервисов, ты ОБЯЗАН выполнить следующие шаги:

1. **Обновить `ARCHITECTURE.md`:**
* Если добавлен новый модуль (например, интеграция с банковским API, вебхук или очереди), внеси его в схему взаимодействия и добавь описание Data Flow.

2. **Обновить `./DATABASE/`:**
* Актуализировать `./DATABASE/schema.sql`, `./DATABASE/DATABASE_DOCUMENTATION.md` и внести изменение в `./DATABASE/changes/`.

3. **Обновить `SYSTEM_PROMPT.md`:**
* Если изменился бизнес-процесс, логика статусов или ролевая модель — отрази это в файле.

---

## 7. ПРАВИЛА СОХРАНЕНИЯ АРТЕФАКТОВ РАЗРАБОТКИ (ARTIFACTS POLICY)

При составлении планов разработки (Implementation Plans) и генерации итоговых отчетов по выполненным шагам (Walkthroughs), ты (AI-агент) ОБЯЗАН сохранять соответствующие `.md` файлы в локальные директории проекта.

### Структура и пути сохранения:
1. **Планы имплементации (Plans):**
   - Путь: `./my_artifacts/implementation_plans/`
   - Шаблон имени файла: `implementation_plan_YYYY-MM-DD-HH-mm.md`
   - Пример: `implementation_plan_2026-07-27-22-30.md`

2. **Пошаговые инструкции и отчеты выполнения (Walkthroughs):**
   - Путь: `./my_artifacts/walkthroughs/`
   - Шаблон имени файла: `walkthrough_YYYY-MM-DD-HH-mm.md`
   - Пример: `walkthrough_2026-07-27-22-35.md`

⚠️ **Форматирование даты:** Использовать текущую системную дату и время (Год-Месяц-День-Час-Минута). Все файлы должны дублироваться и сохраняться на диск.

⚠️ **ВАЖНО:** Задача НЕ считается выполненной, пока соответствующие `.md` файлы не приведены в полное соответствие с новым кодом!

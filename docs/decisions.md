# Решения

Журнал решений, принятых при разработке (кроме решений плана и ТЗ). Новое решение — в конец, с номером по букве потока задачи: «А-1. **…**», перед ним пустая строка (правило — в `CLAUDE.md`, «Параллельные потоки»).

## 2026-10-25. Этап 0

1. **Монорепозиторий pnpm + Turborepo, внутренние пакеты без сборки.** Пакеты экспортируют исходники TypeScript; Next.js транспилирует их (`transpilePackages`), worker собирается tsup в один файл, инструменты запускаются через `tsx`. Так не нужно следить за сборкой каждого пакета.
2. **Версии.** Node 22 LTS, TypeScript 5.9 (typescript-eslint ещё не поддерживает TS 7), Next.js 16, React 19, Hono 4 + @hono/zod-openapi 1 (Zod 4), Drizzle ORM 0.45 + drizzle-kit 0.31, Vitest 5, Playwright 1.63, Tailwind CSS 4. Общие версии — в `catalog:` файла `pnpm-workspace.yaml`.
3. **MinIO — сборка сообщества `pgsty/minio`.** Официальные образы MinIO больше не публикуются в Docker Hub и quay.io. Для docker-compose (разработка, CI, VPS) берём закреплённую версию `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` — тот же MinIO. Код от этого не зависит: он говорит только по протоколу S3, поэтому при необходимости MinIO заменяется на Cloudflare R2, Garage или SeaweedFS без правок кода. Вопрос передан треду «Архитектура и план разработки».
4. **Справочники платформы в этапе 0 — разделы refDB.json как JSONB** (`platform_reference`: ключ раздела, содержимое, контрольная сумма, версия, источник). Модуль «Справочники платформы» (поток Д) разложит разделы по своим таблицам и добавит историю загрузок. ГКЭД сразу в своей таблице `gked_items` с поиском pg_trgm.
5. **Наполнение по умолчанию только добавляет.** `pnpm db:seed` не перезаписывает то, что администратор платформы уже поменял; `--update` обновляет изменившиеся разделы (локально, в CI и на стенде после `pnpm spec:sync`). Демо-организация не создаётся при `APP_ENV=production`.
6. **Один маршрут расписания.** Vercel Cron и worker вызывают только `/api/cron/tick` раз в минуту; расписания задач (cron по Бишкеку) и защита от повторов (`scheduler_runs`, первичный ключ job+slot) — в нашем коде и базе. Vercel Cron вызывает GET, worker и cron на VPS — POST, оба с `Authorization: Bearer <CRON_SECRET>`.
7. **Автослияние — свой workflow, squash.** `automerge.yml` сливает PR, когда последние запуски `check`, `docker-e2e`, `pr-policy` зелёные, PR не черновик и без метки `hold`, ветка не отстала от main. Скрипт берётся из main. Встроенное автослияние GitHub требует защиты ветки, которая для закрытых репозиториев доступна не на всех тарифах; если защита включена, оба механизма работают вместе.
8. **Отчёт агентов-ревьюеров — обязательная проверка.** `pr-policy` требует в описании PR раздел «Отчёт ревьюеров» с выводами `spec-reviewer` и `security-reviewer` и падает, если найдено критичное или несоответствие ТЗ.
9. **Сайт не индексируется** (`robots.txt` — Disallow: /, метатег noindex, API отдаёт `X-Robots-Tag: noindex`) до решения о публичных страницах.
10. **Sentry подключается на шаге развёртывания**: переменная `SENTRY_DSN` уже в схеме настроек; SDK добавим вместе с аккаунтом, чтобы не тянуть его без ключа.
11. **RLS включён у каждой таблицы `public`, политики — только для роли `buhuchet_app`.** Таблицы организаций — изоляция по `org_id`; справочники платформы — только чтение; служебные таблицы (запуски задач) — чтение и запись. У остальных ролей политик нет, поэтому даже если на Supabase останется включённым Data API, ключ anon ничего не увидит и не изменит. Тест `rls.test.ts` падает, если у новой таблицы забыли RLS. Роль входа приложения называется `buhuchet_*`, пароль ей задаётся в виде SCRAM-SHA-256 (открытый пароль не попадает в журнал базы), миграции отказываются работать с ролью, у которой есть права владельца таблиц.
12. **PR, который меняет проверки, автослияние или хуки** (`.github/`, `scripts/automerge.mjs`, `scripts/check-pr-policy.mjs`, `scripts/check-protected.mjs`, `scripts/protected-paths.mjs`, `.claude/hooks/`, `.claude/settings.json`), сам не сливается — сливает заказчик: для `pull_request` GitHub берёт workflow из ветки PR, и такой PR мог бы ослабить проверки сам себе. Шаг CI «Применённые миграции и spec/ не тронуты» не пропускает изменение миграций из main и ручную правку spec/ (только `pnpm spec:sync`, которая меняет `spec/SOURCE.json`). Учитываются только проверки GitHub Actions.
13. **`APP_ENV` обязательна; на стенде и рабочем сайте `CRON_SECRET` — от 32 символов и не из `.env.example`.** Сайт проверяет настройки при запуске (`apps/web/instrumentation.ts`), а не при первом запросе: без нужных настроек он не стартует, как и worker; `next build` настроек не требует.
14. **Пароль владельца базы (`DATABASE_ADMIN_URL`) — только у миграций и наполнения**: в docker-compose он есть только у сервиса `migrate`, в Vercel не задаётся.
15. **Заголовки безопасности.** Страницы: `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy`, HSTS (`next.config.ts`, одинаково на Vercel и VPS); API: `secureHeaders` Hono и `Cache-Control: no-store` по умолчанию. Файлы отдаются только вложением по ссылке не дольше 15 минут.
16. **Миграции стенда — `migrate-test.yml`** (`db:migrate`, `db:seed --update`, `storage:init` с `APP_ENV=staging`) только с кода `main`: после автослияния PR, меняющего `packages/db/` или `spec/data/`, его запускает `automerge.mjs` через `workflow_dispatch` (слияние токеном `GITHUB_TOKEN` не запускает `push`), при слиянии человеком — `push`, иначе вручную. База — через пул Supabase в режиме сеанса (у бесплатного проекта прямое подключение только по IPv6). Секреты — секреты репозитория `TEST_*`, только в шагах, которым нужны (Environment в закрытом репозитории — только на платных тарифах GitHub); необязательные `TEST_DEMO_PASSWORD` (пароль демо-сотрудников) и `TEST_ADMIN_LOGIN`/`TEST_ADMIN_PASSWORD` (администратор платформы стенда) получает только шаг наполнения.
17. **Пользователи, сотрудники и роли (задача #3).** Учётная запись (`users`: логин, хеш argon2id, блокировка, «сменить пароль при входе») отдельно от сотрудника (`employees`: ФИО, телефон, роль, «активен»). Один пользователь — одна организация, поэтому `org_id` лежит и в `users` (пусто только у администратора платформы — это проверяет ограничение таблицы): по нему работает обычная изоляция RLS, а сотрудник, роль, права и область ссылаются на пары `(id, org_id)` и не могут указать на запись другой организации. У роли владельца признак `is_owner` (одна на организацию) и все права по правилу домена, без перечня в `role_permissions`. Набор 39 прав и их группы задаёт код (`PERMISSIONS` в `@buhuchet/domain`), названия и описания — справочник `permissions` из refDB; наполнение останавливается, если refDB расходится с кодом. Задачи по расписанию получают список организаций функцией `app.org_ids()` (SECURITY DEFINER, только номера) и обходят их по одной в `withOrgContext`. Блокировок две, и они не снимают друг друга: `users.blocked` ставит администратор платформы, `employees.active = false` — владелец организации; войти нельзя ни при одной из них. Привязка Telegram — отдельная таблица задачи #6, счётчик неверных паролей — задача #5, тема — #13, состояние приветствия и опросника — «Моя организация».
18. **Организация создаётся ролью приложения под RLS** (`createOrganization` в `@buhuchet/db/organizations`): одна транзакция от имени новой организации — роли из шаблонов платформы, владелец с временным паролем, учётная политика по умолчанию. Так же её будет создавать Админка. До Админки — служебные команды `pnpm db:create-org` и `pnpm db:create-admin` (администратору платформы нужен владелец схемы, потому что у него нет организации); временный пароль печатается один раз, поэтому в GitHub Actions они не запускаются. Администратора платформы стенда создаёт наполнение из `PLATFORM_ADMIN_LOGIN`/`PLATFORM_ADMIN_PASSWORD` (секреты `TEST_ADMIN_*`, 27.10.2026, просьба заказчика): только если его нет, с временным паролем; уже созданного не трогает. Демо-сотрудники входят паролем из `DEMO_PASSWORD` (на стенде — секрет `TEST_DEMO_PASSWORD`); пока он ни разу не задан, войти в демо-организацию нельзя; новый пароль наполнение ставит с выходом со всех устройств, но без сообщения в Telegram — это служебная смена общих демо-учёток стенда, а не смена пароля пользователем.
19. **История изменений и версия записи (задача #4).** Одна общая таблица `audit_log` для всех записей организации («одна таблица истории на всё», как в «Основных паттернах»): вид записи и её номер, действие, изменённые поля «было → стало» (JSONB), причина, контрагент (для истории в карточке контрагента), автор и время. Организация, автор и время подставляются базой из контекста транзакции (`app.org_id`, `app.user_id`, `now()`); ограничивающая политика вставки не даёт записать другого автора, другое время или пользователя чужой организации (автором может быть только пользователь этой организации или администратор платформы — проверка `app.history_actor_allowed`, SECURITY DEFINER); без пользователя автор — «Система». Записи только добавляются: у роли приложения нет прав UPDATE и DELETE на таблицу. Значения секретных полей (по списку и по окончанию имени Hash, Token, Secret) не пишутся — только факт изменения. Правка записи с версией (`updateWithHistory`) принимает только столбцы таблицы без служебных, блокирует строку до конца транзакции (`SELECT … FOR UPDATE`) и сверяет версию: устаревшая → `RecordChangedError` → 409 `record_changed`; так вторая из одновременных правок ждёт первую и получает предупреждение, а не затирает её. Условие области «Свои контрагенты» передаётся в тот же запрос (`where`), запись вне области — 404, как чужая. Ошибки запросов к базе пишутся в журнал без значений параметров. Пока не сделано и решается вместе с модулями: история платформы (справочники, администратор без организации — столбец `org_id` обязателен), автор «Контрагент (по ссылке)» и пометка источника («Из Excel», «по опроснику»), история статусов с откатом (#17).
20. **Вход и сеансы (задача #5).** Сеанс — 32 случайных байта в cookie `__Host-bh_session` (HttpOnly, Secure, SameSite=Lax, Path=/; локально и в сквозных тестах по http — `bh_session` без Secure), в таблице `sessions` — только SHA-256 токена. Сеанс живёт 30 дней с последнего обращения (docs/deviations.md, п. 5) и продлевается не чаще раза в час (тогда cookie выдаётся заново). Вход, проверка cookie и выход идут до того, как известна организация, поэтому они — узкие функции `app.auth_*` (SECURITY DEFINER, только для роли приложения), а не чтение таблиц в обход RLS. Пять неверных паролей подряд закрывают вход на 15 минут. Счёт ведётся по набранному логину, есть такой логин или нет (таблица `login_attempts` без организации; роль приложения её не видит, только функции `app.auth_login_*`), поэтому «вход закрыт» одинаков для любого логина; через час после последней попытки счёт забывается, такие строки каждые 10 минут удаляет задача `auth.cleanup-login-attempts` (на скорость подбора срок не влияет: её задают 5 попыток на 15 минут, а таблица не растёт от выдуманных логинов дольше часа). Попытка занимается в базе до проверки пароля (`app.auth_login_attempt`, строка логина блокируется до конца функции), а пока вход закрыт, пароль не проверяется вовсе: одновременные запросы не проверят больше пяти паролей. Верный пароль, смена пароля, код из Telegram и временный пароль снимают счёт. Неверный текущий пароль при смене пароля считается так же (иначе украденный сеанс позволял бы подбирать пароль без ограничения), и пятый такой ответ — тоже «вход закрыт». Выход удаляет сеанс, смена пароля — все остальные сеансы пользователя, а текущему выдаёт новый токен: старая cookie не действует нигде. Блокировка сотрудника, учётной записи или организации (`organizations.status`; причина — необязательная пометка администратора) закрывает и уже открытые сеансы при следующем запросе; тексты — как в прототипе (сотрудник, которого заблокировал и владелец, и администратор платформы, видит «Обратитесь к владельцу организации»); при входе о блокировке сообщается только после верного пароля. Общий слой API: все пути, кроме открытых (`/api/health`, `/api/cron/tick`, `/api/openapi.json`, вход и выход), требуют сеанс (401); с временным паролем доступны только «кто я» и смена пароля (403 `password_change_required`); для сотрудника права и области загружаются в контексте его организации; право метода — `requirePermission` в `createRoute`; организация метода — только из сеанса (`orgContextOf`). Изменяющие запросы (всё, кроме GET, HEAD, OPTIONS) принимаются только с заголовком Origin нашего адреса — `APP_BASE_URL` или Host запроса; заголовкам прокси (X-Forwarded-Host) не верим; без Origin пропускаются только вызовы планировщика с секретом. Тело запроса API — не больше 1 МиБ (файлы идут в хранилище мимо API). Cookie с `Secure` и `__Host-` — на стенде, рабочем сайте и любом сайте по https; на стенде и рабочем сайте `APP_BASE_URL` обязателен и только https (сайт без него не стартует). Пока не сделано: лимит попыток входа с одного IP (нужен до рабочего сайта: без него выдуманные логины наполняют `login_attempts`, а один пароль можно пробовать на многих логинах), запрет менять служебные столбцы (`organizations.status`, `users.blocked`, счётчик паролей) обычными методами на уровне базы — методы «Моя организация» и «Сотрудники» (#7, #8) собирают правку из явного списка полей, а меняет их только Админка (#18). Администратор платформы входит без организации и прав в организациях не имеет. Неизвестный логин и неверный пароль — одно сообщение «Неверный логин или пароль» и одно время ответа (docs/deviations.md, п. 4, решение Б).
21. **Telegram и «Забыли пароль?» (задача #6).** Привязка — отдельная таблица `telegram_links` (у пользователя один чат, один чат — у нескольких логинов, тогда в сообщениях первой строкой идёт организация). Ссылка «Скопировать ссылку» — `t.me/<TELEGRAM_BOT_USERNAME>?start=<токен>`: 32 случайных байта, в базе только SHA-256 (`telegram_link_tokens`), действует 15 минут, у пользователя — только последняя; использованная остаётся с отметкой, чтобы повтор того же сообщения Telegram не ответил «ссылка недействительна». Если вместо прежнего привязан другой чат, бот пишет об этом в прежний (`tgRelinked`), при отвязке — в отвязанный (`tgUnlinked`): привязка — способ восстановить пароль, и чужая замена по украденному сеансу не должна пройти незаметно. Вебхук `/api/telegram/webhook` открыт без входа и без Origin, но принимается только с секретом `TELEGRAM_WEBHOOK_SECRET` в заголовке `X-Telegram-Bot-Api-Secret-Token`, проверка — до разбора тела; без бота (нет токена) метода как будто нет (404). Бот отвечает только на текст в личном чате; на остальное — 200 без ответа, чтобы Telegram не повторял доставку. Вебхук сайт ставит сам: задача по расписанию `telegram.register-webhook` каждые 10 минут вызывает `setWebhook` с адресом `<APP_BASE_URL>/api/telegram/webhook` и секретом, если бот задан и адрес по https (повтор с теми же данными ничего не меняет, смена секрета подхватывается сама); токен — только в окружении (docs/deviations.md, п. 14). «Забыли пароль?» для любого логина отвечает одинаково и не быстрее 1,5 с (`RESET_RESPONSE_FLOOR_MS`), чтобы ни текстом, ни временем не было видно, есть ли логин и привязан ли Telegram (docs/deviations.md, п. 4, решение Б); код уходит, только если логин есть, не заблокирован, Telegram привязан и лимиты позволяют. Код — 6 случайных цифр, в базе — хеш argon2id (`password_reset_codes`), 10 минут, не больше 3 в час на логин, новый код отменяет прежний; лимиты проверяются функцией `app.auth_reset_status` до того, как считать хеш (запросы сверх лимита не нагружают сервер), и ещё раз под блокировкой строки пользователя в `app.auth_reset_request` (одновременные запросы их не превысят). Запрос, на который Telegram не принял сообщение, тоже считается: код записывается до отправки. ТЗ не ограничивает число вводов кода, но без ограничения 6 цифр перебираются за 10 минут, поэтому ввод занимается до проверки, как попытка входа (`app.auth_reset_attempt`): после 5 неверных код не действует; после 10 неверных за 24 часа коды не присылаются и не принимаются 24 часа после последнего кода (иначе 15 вариантов в час без конца — около 1 % за месяц на учётную запись; docs/deviations.md, п. 9). Текст ошибки всегда один — «Код неверный или истёк», и для неизвестного или заблокированного логина тоже. Верный код задаёт новый пароль, закрывает все сеансы и снимает блокировку входа после неверных паролей; сеанс не создаётся — войти нужно новым паролем, как в прототипе. Ожидающий код отменяется (`app.auth_reset_revoke`), когда пароль сменили в профиле или сбросили временным, когда Telegram отвязали или заменили другим чатом: код, отправленный раньше, пароль уже не задаст. Код, ответы бота и служебные сообщения уходят сразу через переходник `telegram` (ответа Telegram ждём не дольше 10 с, кода — 1 с, чтобы медленный Telegram не выдал по времени, что логин есть), мимо очереди (очередь и журнал отправок — поток Б, docs/deviations.md, п. 12); ошибка Telegram пишется в журнал сервера без текста сообщения. Бот сообщает о каждой смене пароля: по коду и в профиле — `tgPassChanged`, сброс временным паролем — `tgPassReset` с тем, кто сбросил. Сброс временным паролем: сотрудник с правом «Сотрудники и роли» (по умолчанию только владелец) — любому сотруднику, кроме владельца (`POST /api/staff/{id}/password-reset`, как в прототипе; docs/deviations.md, п. 11); администратор платформы — любому пользователю организации (`POST /api/admin/users/{id}/password-reset`, действует в контексте её организации и пишет в её историю; учётную запись он находит функцией `app.admin_find_user`, которая отвечает только администратору). Временный пароль показывается один раз, в историю пишется только факт смены. Шаги без входа и без организации — функции `app.telegram_*`, `app.auth_reset_*`, `app.admin_find_user` (миграция 0011, SECURITY DEFINER, только для роли приложения); изменение от имени пользователя — только для `app.current_user_id()` в его `withOrgContext`, с историей в той же транзакции. Таблицы `telegram_links`, `telegram_link_tokens`, `password_reset_codes` роль приложения только читает (под RLS), а меняет — только этими функциями: ошибка в коде не обнулит попытки и не перепривяжет чужой Telegram. Будущий предел неверных попыток с одного IP должен покрывать и `/api/auth/password-reset*`: пачка одновременных запросов на один логин ещё успевает разово посчитать argon2 до записи кода. Пароль для привязки Telegram не спрашивается, сброс пароля Telegram не отвязывает — как в прототипе, решение заказчика (docs/deviations.md, п. 13). Демо-сотрудникам Telegram не привязывается: выдуманный chat_id мог бы оказаться чужим человеком (docs/deviations.md, п. 10).
22. **Сотрудники и роли (задача #7).** Правило галочек роли — одна функция домена для формы (#18) и сервера: `rolePermissionLock` повторяет `roleLock` прототипа и сверена с ним на ролях demoDB (702 ответа, фикстура `packages/domain/src/roles/__fixtures__/role-locks.json`, скрипт `packages/domain/scripts/oracle-roles.mjs`); `roleChangeProblem` проверяет сохранённый набор: добавленное право — полностью («Сначала дайте просмотр» по новому набору, право только владельца, «выдаёт только владелец», своя роль), снятое не держит (право группы без просмотра всё равно не действует, а прототип оставляет его в роли). Роль владельца и свою роль (не владельцу) сервер не меняет вовсе; роль с правами «выдаёт только владелец» меняет, удаляет, назначает и снимает только владелец, и только он сбрасывает пароль, блокирует и разблокирует её носителей. Не владелец не выдаёт больше, чем есть у него (`roleWithinRights`): правка роли сравнивает действующие права и область до и после (в том числе ожившие с возвращённым просмотром группы), а роль шире своей он не назначает новому сотруднику и при смене роли, не сбрасывает пароль, не блокирует и не разблокирует её носителей (docs/deviations.md, п. 15). Решение о сотруднике читает его роль с блокировкой строки на чтение (`roleAccess`, FOR SHARE), а правка роли блокирует её на запись (`lockRole`), поэтому решение не опирается на права, которые в ту же секунду меняют; сброс пароля блокирует и самого сотрудника. Сохранение роли — одна правка с версией: изменения прав и области (только переданные группы) пишутся в историю роли полями `permissions` и `scopes` «было → стало», смена роли сотрудника — ещё и названиями ролей (`roleName`), чтобы история читалась и после удаления роли. Права загружаются при каждом запросе, поэтому новая роль и новые права действуют сразу; блокировка ещё и удаляет сеансы сотрудника в той же транзакции. Логин уникален на всей платформе: «Такой логин уже занят на платформе» (как в прототипе) видят только сотрудники с правом «Сотрудники и роли» при создании сотрудника — это ответ ограничения уникальности базы, чужие учётные записи RLS не показывает. Временный пароль нового сотрудника задаёт владелец (от 8 символов) или сервер (docs/deviations.md, п. 17); в историю идёт только факт создания с ФИО, телефоном и ролью. Удаляется только роль без сотрудников (и заблокированных) и не роль новых сотрудников; если её назначили в ту же минуту, удаление останавливает внешний ключ. Отказ по правилу внутри транзакции — `apiFail` (`packages/api/src/errors.ts`): транзакция откатывается, ответ в общем формате. Счёт, реквизиты для переводов (видны самому сотруднику, владельцу и главному бухгалтеру по ТЗ, а в прототипе — тем, у кого «Сотрудники и роли»: расхождение запишем с задачей о реквизитах), уровень знаний и число контрагентов и отчётов сотрудника добавят их модули; передача контрагентов при блокировке — вместе с контрагентами (поток А).

24. **Локализация (задача #9).** Словарь текстов интерфейса — таблица `ui_texts` (язык, ключ, текст, раздел, кто завёл и кто поправил в Админке, время, версия; ключ — пара «язык + ключ»), общая для всех организаций: роль приложения только читает (RLS), меняет администратор платформы (экран «Локализация» и загрузка из Excel — поток Д). Наполнение — раздел `localization` refDB.json (тексты прототипа) и тексты экранов продукта `UI_TEXTS` (`@buhuchet/domain`): ключ из обоих мест берётся из refDB.json, тест следит, чтобы тексты совпадали. `db:seed --update` обновляет только тексты из наполнения: поправленный в Админке (`updated_by` задан) не затирается. Метод `GET /api/l10n` открыт без входа (словарь нужен на странице входа): тексты базы поверх `UI_TEXTS`, поэтому ключ, выложенный с новым кодом раньше наполнения, всё равно показывается; версия словаря — в ETag, браузер перепроверяет его (`no-cache`) и получает 304, пока словарь тот же. API держит словарь в памяти и не чаще раза в секунду сверяет его с отметкой базы (число текстов и хеш пар «ключ — текст»): перечитывает, только когда она изменилась, — так и текст, поправленный прямо в таблице, виден со следующего обновления страницы. Роль приложения только читает словарь: права на запись забраны (миграция 0017), RLS разрешает только чтение; правку из Админки сделает узкая функция для администратора платформы. База недоступна — отдаются тексты `UI_TEXTS` без кэширования, чтобы страница (в том числе «здоровье») всё равно показалась. Первый показ без мигания: корневой макет сайта берёт словарь на сервере тем же методом API в том же процессе (`apps/web/src/l10n/server.ts`), страница приходит уже с текстами, экраны берут их хуком `useT()`, серверные компоненты — `getT()`; ключ проверяется типом (`UiTextKey`). Строки с русскими буквами в коде `apps/web` и `packages/ui` запрещает ESLint (`no-restricted-syntax`), правило проверяет тест. Пока не сделано, придёт со своими задачами: сообщения ответов API (ошибки) — в коде сервера; экран показывает их через `useErrorText()` из словаря по коду (`err.<код>`), а текст ответа — только если ключа нет, ключи `err.*` заводятся вместе с экранами; раздел `localization` пока копируется и в `platform_reference` (наполнение этапа 0) — источник словаря только `ui_texts`, копия уйдёт, когда «Справочники платформы» разложат разделы по таблицам; тексты сообщений Telegram и значения справочников переводятся, когда языков станет больше (ТЗ); список языков и «сколько строк переведено» — с экраном «Локализация».

28. **Вход и «Мой профиль» (задача #13).** Страница `/login` — одна карточка с шагами (`apps/web/src/auth/login-screen.tsx`): вход → «Забыли пароль?» (логин → код из Telegram и новый пароль) → снова вход с подставленным логином; вход с временным паролем → «Смените временный пароль» (только что введённый временный пароль второй раз не спрашивается, после перезагрузки страницы — спрашивается; страницы за входом ведут обратно сюда) → «Привяжите Telegram», если он не привязан и бот подключён к платформе. Привязать Telegram предлагается после смены временного пароля, а не при каждом входе без Telegram: каждая настоящая учётная запись начинается с временного пароля, дальше напоминает предупреждение в «Моём профиле»; «Позже» ведёт в программу. Подсказки «Демо: логины …» прототипа на странице входа нет — она только для прототипа. Неверный логин или пароль — ошибка под паролем с общим предупреждением о блокировке (п. 4 расхождений, дополнение), блокировка сотрудника или организации — под логином. Формы — React Hook Form со схемами `LoginForm`, `PasswordResetLoginForm`, `PasswordResetCodeForm`, `ChangePasswordForm` из `@buhuchet/shared`: сообщения схем — ключи словаря (`auth.err.*`, числа правил подставляет `fieldErrorText`), ошибка ответа API ставится полю с типом `server` текстом `useErrorText()`; поля регистрируются до разметки в порядке экрана, чтобы фокус вставал на первое неверное поле. Запросы — `callApi` (`apps/web/src/api-client.ts`): данные или ошибка `{ code, message, details }`, сбой сети — код `network`. Тексты ошибок ответов входа заведены в словарь (`err.invalid_credentials`, `err.login_locked`, `err.org_blocked` и другие — те же тексты, что у сервера): подстановки берутся из `details` ответа (`time`, `minutes`, `org`), вариант текста — из `details.variant` (`err.user_blocked.platform_admin`, `err.telegram_unavailable.reset`); не хватает значения — экран показывает текст сервера. Поля форм — `Field`, `FormGrid`, `KeyValues`, `Box`, `Note`, `Pill` и `inputClass` в `packages/ui/src/form.tsx` (`fld`, `setErr`, `.kv`, `.box`, `.note`, `.pill` прототипа); на телефоне до 600 px `FormGrid` и `KeyValues` раскладываются как `packForm` и `packKv` прототипа (`ui/mobile-pack.js`): два коротких поля — в строку, длинное — во всю ширину, распорки скрыты; ширину подписей и значений `useFormPack` меряет на холсте, правила — чистые функции `form-pack.ts` с тестами. «Мой профиль» — окно-карточка (`apps/web/src/profile/profile-window.tsx`) из левой панели на ПК и из панели «Меню» на телефоне (с инициалами и ФИО): «Основное» (ФИО, логин, телефон в виде «+996 555 100 200» — `formatPhone` по кодам стран справочника, роль), Telegram (привязан — имя и «Отвязать»; не привязан — предупреждение, ссылка и «Скопировать ссылку»; привязку экран узнаёт, спрашивая «кто я» раз в 3 секунды), «Личные настройки» (тема применяется сразу и хранится в cookie `bh_theme`) и «Смена пароля»; «Мои реквизиты», уровень знаний с «Показывать всё заново» (обучение, поток Г) и «Уведомления в Telegram» владельца и главного бухгалтера (поток В) придут со своими задачами. Ссылки привязки запрашиваются по одной: каждая новая отменяет прежние, и на экране должна остаться выданная последней. Карточка с несохранёнными изменениями (`dirty`) теперь тоже спрашивает «Закрыть без сохранения?» на протяжку вниз и «Назад» и учитывается при выходе (раньше — только форма, п. 27); у профиля `dirty` — пока в «Смене пароля» что-то введено. Окно закрывает панели, и нажать «Выйти» при открытом окне нельзя; правило «Выйти без сохранения?» остаётся на случай выхода не из панели и проверяется сквозным тестом нажатием скрытой кнопки. Бот-подделка сквозных тестов `e2e/fake-telegram.ts` (порт 8091, запускает Playwright) отвечает как Bot API на `sendMessage` и `setWebhook` и отдаёт тестам отправленные сообщения; сайт говорит с ней через `TELEGRAM_API_BASE` (`.env.example`; из Docker — `host.docker.internal`, `extra_hosts: host-gateway`). 29. **Списки — UnifiedDataGrid (задача #14).** Сортировку, страницы и фильтры считает сервер, в браузер приходит только текущая страница разрешённых записей: `selectListPage` (`packages/db/src/list.ts`) строит `where` и `order by` только по объявленным столбцам списка (ключ — как у столбца экрана; чужой ключ — 400), число записей и итоги — оконными функциями в том же запросе (`count(*) over ()`, `sum(...) over ()`), страница за концом списка — последняя. Параметры запроса — `sort=<столбец>.asc|desc|none` (нет — по умолчанию «Создано», от новых к старым; экран всегда шлёт явную), `page` с 1, `size=25|50|100|all` («Все записи» — не больше 5 000 строк за запрос), `filters` — JSON фильтров по типу столбца (текст, значения, число «от — до», дата «с — по»; дата момента — по Бишкеку); интерфейс фильтров и поиск — задача #15, правила сервера уже есть. Текст сортируется естественно и без учёта регистра правилом `app.ru_natural` (ICU `ru-u-kn`, миграция 0019): «Номер 2» перед «Номер 10», ё как е, пустые — в конце. Столбец, которого нет ни в показанных, ни в скрытых (появился позже), получает видимость по умолчанию. Экран берёт все настройки пользователя одним запросом и сохраняет правку через 300 мс после последней (при закрытии страницы — сразу, `keepalive`). Компонент — свой (`packages/ui/src/grid/`), без TanStack Table: при серверных страницах таблице нечего считать, а правила вида (порядок, ширины, видимость) — чистые функции с тестами, как в прототипе; данные экранов — TanStack Query (`apps/web/src/query.tsx`). В списке сотрудников пока столбцы, которые уже есть в базе (ФИО, логин, телефон, роль, Telegram, последний вход, статус и служебные); «Контрагентов», «Несданных», «Просрочено», «Баланс счёта» и «Уровень знаний» добавят их модули. 30. **Списки — поиск, фильтры, группировка, «В Excel» и «Статистика» (задача #15).** Поиск из верхней панели, фильтры у столбцов и группировка считаются на сервере тем же запросом, что страница (`selectListPage`). Поиск — как `compute` прототипа (`searchCondition`, эталон `matchesSearch` в `@buhuchet/domain`): подстрока в тексте **видимых** столбцов (`q`, `qcols`) без учёта регистра и «ё», а с трёх значащих символов — ещё и без пробелов, дефисов, скобок и запятых (телефон, ИНН, сумма); текст столбца-кода (статус, Telegram) — подпись из словаря, как на экране (`ListColumn.display`, тексты — `serverTexts`). Фильтр у столбца — меню под значком в заголовке (`FilterPanel` в `FloatingPanel`, окно вынесено в `body`, чтобы его не обрезала прокрутка таблицы): текст — «содержит», значения — галочки с числом записей во всём списке и «(Пусто)» из метода `…/values?col=` (`selectListValues`, не больше 500 значений), число «от — до» (деньги вводятся в сомах), дата «с — по». Активные фильтры, поиск и группировка — плашки над списком; «Сбросить всё» снимает фильтры и поиск, группировку оставляет. Фильтры и поиск не запоминаются (живут на экране, при смене поиска, фильтра или группировки — первая страница). Группировка — до двух уровней (`group=a,b`), в настройках вида вместе с итогами групп (`agg`): группы, число записей и итоги считаются по **всем** отфильтрованным записям, по запросу на уровень (`selectGroups`; подпись группы — `min(подписи)`, потому что подписи из словаря — параметры запроса и не совпадают с выражением `group by`); порядок групп — порядок столбца (роль по названию, «Активен» выше «Заблокирован»), пустая группа внизу. По умолчанию у числовых столбцов — сумма (решение п. 33), выбор — «Сумма / Среднее / Минимум / Максимум / Количество / Не считать». Сгруппированный список приходит одной порцией до 5 000 записей (страницы делить группы не должны), строки раскладываются по группам ключами `rowGroups`; свёрнутые группы — только на экране и сбрасываются при смене группировки. «В Excel» (по праву «Выгружать в Excel», решение п. 32) — метод `…/export` с теми же параметрами и видимыми столбцами по порядку экрана (`cols`): файл `.xlsx` собирает сервер без библиотеки (`packages/api/src/lists/xlsx.ts`: один лист, заголовок жирным, закреплён и с автофильтром, деньги — в сомах с форматом «1 250,50», текст — строкой, поэтому «=…» не становится формулой), не больше 50 000 строк (`EXPORT_ROWS_LIMIT`); сколько строк вошло — в заголовках `x-export-rows` и `x-export-more`, экран говорит это уведомлением. «Статистика» модуля (плашки-итоги над списком, `Plates` и `Plate` в `packages/ui`, нажатие на плашку фильтрует список) — кнопка в ряду вкладок (`StatsToggle`) только у вкладок из `SCREENS_WITH_PLATES` (`apps/web/src/screens/module-screen.tsx`); показана ли она — настройка вида `stats.<модуль>` (`isViewKey`), отдельно для ПК и телефона (по умолчанию на ПК показана, на телефоне скрыта). Плашки и их фильтры добавляют экраны модулей; «Ещё фильтры» из задачи нет ни в ТЗ, ни в прототипе — фильтры стоят у каждого столбца.

32. **Фильтр-галочки — «Найти значение» по всем значениям и «Выбрать все» с не показанными (уточнение ТЗ 26.10.2026 к п. 34 расхождений).** В окно фильтра приходят первые 500 значений (`LIST_VALUES_LIMIT`) и сколько их всего (`total`); подсказка — «Показаны первые 500 значений из 1 240 — сузьте список поиском». Если пришли не все, «Найти значение» ищет на сервере (`…/values?col=&q=`, подпись значения содержит текст без учёта регистра и «ё»; эталон `matchesValue`, «(Пусто)» поиском не находится, как в прототипе). Выбор хранится шагами, а не списком всех отмеченных: фильтр `{type:'enum', vals, steps}` — отмеченные значения, а после них по порядку «отметить / снять значения» и «отметить / снять все, подпись которых содержит …» (`match`, '' — все); значение отмечено, если так решил последний касающийся его шаг (`enumChecked`, на сервере — `case when … end` в `filterCondition`). Так «Выбрать все» по поиску отмечает и значения, которых человек не видел, а выбор совпадает с прототипом, где все значения в браузере (проверено перебором последовательностей в тестах домена). Шаги упрощаются на месте (`addEnumStep`: новый шаг убирает перекрытые значения и более узкие поиски, шаг без изменений не добавляется), без поиска выбор остаётся обычным списком; «Выбрать все» отмечена, только если отмечены все подходящие, в том числе не показанные (`enumMatchChecked`, в сомнении — не отмечена). Если пришли все значения, уходит список отмеченных, как в прототипе, а если он длиннее 200 — шаги или «все, кроме» снятых. Фильтр едет в адресе запроса, поэтому в нём не больше 200 отдельных значений и 20 шагов; больше — окно просит выбрать поиском и «Выбрать все» (docs/deviations.md, п. 36). Окно фильтра переставляется при смене размера, чтобы не выходить за край экрана.
33. **Шкала статусов и «История статусов» (задача #17).** Правила шкал — в `@buhuchet/domain` (`common/status.ts`): шаги, боковые статусы, «Не требуется», отметки подтверждения сдачи, следующий шаг (`scaleNext`), шаг для отката (`scaleBack`), запрет отката (`rollbackRefusal`: нет права «Откат статусов», не на шаг назад, пустая причина), время в статусе и итоги; ответы сверены с функциями прототипа (`scripts/oracle-status.mjs` → `__fixtures__/status-scales.json`). Статусы хранятся кодами (`todo`, `in_progress`, …), названия — в словаре (`status.<шкала>.<код>`), цвет и значок — по справочнику «Статусы». История — отдельная таблица `status_history` (шкала, запись, было → стало, откат, причина, автор, время), а не `audit_log`: её читают постоянно (карточка, время в статусе), и у каждой шкалы свой список кодов, который проверяет база. Пишется `writeStatusChange` в той же транзакции, что меняет статус; организация, автор и время — из контекста, как у `audit_log`; записи только добавляются (у роли приложения нет UPDATE, DELETE, TRUNCATE); откат без причины база не примет. Новый код статуса на шкале — новая миграция ограничения. Файла в истории пока нет: столбец придёт с модулем «Файлы», компонент его уже показывает. Общих методов API нет: смену статуса и откат делает модуль записи (отчёты, задачи, проекты, …) со своими правами и условиями шага, беря `readStatusHistory`, `rollbackRefusal` и схему `StatusRollback`; доступ к самой записи (область «Свои контрагенты») модуль проверяет до чтения и записи истории — у `entity_id` нет внешнего ключа, RLS отделяет только организации — и закрепляет тестом «вне области — не найдена». Компоненты — `StatusScale`, `StatusMini`, `StatusNone`, `StatusHistory`, `RollbackDialog` в `@buhuchet/ui`, перевод в их пропсы с текстами словаря — `apps/web/src/status/status-view.ts`. Проверяются на странице образцов `/samples` (демо-записи только в браузере, после входа; на рабочем сайте — 404), пока экранов модулей нет.

36. **Справочники платформы для контрагентов и отчётов (задача #20).** Справочники, на которые будут ссылаться контрагенты и отчёты, лежат в своих таблицах с внешними ключами (`packages/db/src/schema/platform-dicts.ts`, миграции 0022 и 0023): «Органы» `authorities` (к списку задачи добавлены: вид отчёта и его платежи ссылаются на орган), «Режимы налогообложения» `tax_regimes`, «Основания для отчётов» `report_bases`, «УГНС» `tax_offices`, «Виды отчётов» `report_types` со связями `report_type_regimes` (режим «применяется» или «не применяется») и `report_type_bases`, «Налоговые льготы и особые статусы» `tax_benefits` со связями `tax_benefit_report_types` (добавляет или убирает вид отчёта), `tax_benefit_offices` («ставится по УГНС»; в refDB.json — `suggest.ugns`) и `tax_benefit_due_rules` (льгота меняет сроки), производственный календарь `production_calendar` (праздники, переносы и рабочие субботы). Остальные мелкие разделы refDB.json остаются в `platform_reference`; разделы со своими таблицами (и «Права», «Шаблоны ролей», «Локализация», у которых таблицы с этапа 0) туда больше не копируются, `db:seed --update` удаляет их старые копии (п. 24 это предусматривал). Ключ каждой записи — постоянный код из refDB.json: у видов отчётов — `id` («nds»), у УГНС — `id`, а код ГНС — отдельное поле (у части УГНС его ещё нет; контрагент демо-организации с «020» найдёт УГНС по коду ГНС); у календаря — день (`MM-DD` — праздник каждый год, `YYYY-MM-DD` — на дату). Значение не удаляется, а отключается (`active`); используемое значение удалить не даёт внешний ключ. У каждой записи — порядок справочника, версия, кто завёл и кто поправил в Админке. Сверку вида отчёта с ГНС (дата и кто сверял) показывает только Админка, как в прототипе: в методах для организаций её нет.
    - Роль приложения справочники только читает (RLS и `REVOKE` записи, как у `ui_texts`); правка — Админка (поток Д, с историей изменений по ТЗ). Методы чтения — `GET /api/report-types`, `/tax-regimes`, `/tax-benefits`, `/report-bases`, `/tax-offices`, `/authorities` для любого вошедшего: по умолчанию только действующие значения (отключённое не предлагается в новых записях; отключённый вид отчёта не приходит и в видах основания и в «добавляет» льготы), с `all=true` — все, для уже созданных записей; `GET /api/production-calendar?year=` — праздники, переносы и рабочие субботы года (правила дня — `isWorkingDay`, `nextWorkingDay` в `@buhuchet/domain`, сверены с прототипом).
    - Наполнение (`seedPlatformDicts`): схемы строгие, ссылки по названиям из refDB.json (орган вида и его платежей, режимы) переводятся в коды; они и коды оснований, УГНС, видов отчётов, льгот, ставок ЕН, форм собственности и налогов (последние три — без внешнего ключа: ставки ЕН и формы с задачи 2.01 в своих таблицах, налоги — в `platform_reference`) проверяются до записи — неизвестное значение или повтор кода останавливают наполнение с понятной ошибкой. Без `--update` добавляются только новые записи со связями; с `--update` изменившиеся записи обновляются (версия +1) и их связи приводятся к refDB.json, а поправленные в Админке (`updated_by` задан) не трогаются; записи, которых в refDB.json нет, не удаляются. Исключение — календарь: он сопоставляется по дате, и `--update` удаляет дни из наполнения, которых в refDB.json больше нет (перенесённая предварительная дата айта не останется праздником); заведённые и поправленные в Админке дни не трогаются. История изменений справочников начинается с Админки (поток Д): наполнение — выпуск данных из `spec/`, его след — коммит refDB.json.
    - Не переносятся поля, которые прототип выводит или не использует: у видов отчётов `payOnly` и `sum` (следуют из «что сделать» `act`), `range` и `rate` (не используются), у всех — служебные `_cb/_ca/_ub/_ua` прототипа. Основания вида отчёта берутся из поля `basis` вида (`bases.types` в refDB.json — обратная ссылка, у трёх отключённых видов она расходится). Срок «последний день месяца» у льгот (`dueOverride: 'last'`) хранится числом 31.

38. **Защита тяжёлых запросов (этап 2, общая задача до потоков; предложило ревью безопасности задачи #15, решение 26.10.2026).**
    - Предел времени запроса к базе — `statement_timeout` через `set_config(…, true)` в начале транзакции `withOrgContext` и `withUserContext`, своим значением для вида работы (`QueryKind`, `QUERY_TIMEOUT_MS` в `packages/db/src/context.ts`): `request` — методы и списки (поиск, фильтры, группы), 15 с; `export` — «В Excel», 60 с; `job` — задачи по расписанию и worker, 4 минуты. По умолчанию — `request`; задача по расписанию сама передаёт `kind: 'job'`. Запросы вне транзакции (вход, проверка сеанса, служебные очистки) короткие и предела не получают.
    - Задачи — 4 минуты (так и в плане): функция `/api/[[...route]]` на Vercel живёт не дольше 300 с (`maxDuration = 300`), и задача должна упасть с записью в `scheduler_runs` раньше, чем платформа оборвёт функцию. Worker на VPS этим не ограничен. Общего предела у роли базы (`ALTER ROLE … SET statement_timeout`) нет: запросы вне транзакции — короткие функции входа, сеанса и частоты, а длинные служебные работы (наполнение, миграции) идут от владельца схемы.
    - Запрос дольше предела база прерывает (код 57014, `queryTimedOut`); общий обработчик API отвечает 503 `query_timeout` и пишет в журнал предупреждение с путём. Формы показывают общий текст ошибок `err.query_timeout` («Запрос выполнялся слишком долго. Попробуйте ещё раз.»); список, значения его фильтров-галочек и «В Excel» — `grid.query_timeout` с советом сузить список (`limitFailureText` в `apps/web/src/lists/limit-text.ts`; `errorText` и `errorTextOf` у `DataGrid`, `ApiFailure` в `apps/web/src/api-client.ts`). Причину вместо «Проверьте подключение к интернету» экраны показывают только для пределов этой задачи (`query_timeout`, `export_busy`, `export_limit`); другие ошибки сервера — как прототип. Такой запрос не повторяется сам (`retryOnce`; карточки и значения фильтров тоже бросают `ApiFailure`).
    - «В Excel» — одна выгрузка пользователя одновременно и не больше 20 за час (`EXPORT_HOURLY_LIMIT`, `EXPORT_RATE_LIMIT`, `withExportSlot` в `packages/api/src/lists/export.ts`): иначе 429 `export_busy` или `export_limit`. Выгрузка отпускается, чем бы ни кончилась; не отпущенная (сбой процесса) перестаёт мешать через 5 минут — столько живёт функция API: 60 с — предел каждого запроса, а не всей выгрузки. Запрос с фильтрами или страницей не в формате отвечает 400 до счёта; неизвестный столбец база отклоняет уже внутри выгрузки — попытка считается, но выгрузка сразу отпускается. Администратор платформы считается так же. Общего предела выгрузок на организацию и заголовка `Retry-After` пока нет: одновременно у сотрудника одна выгрузка, а пул соединений и память проверит нагрузочная проверка этапа 3.
    - Счёт — общая таблица `rate_limits` (миграция 0026): строка — одно действие вида `kind` от `subject`, `busy_until` — пока идёт. Роль приложения таблицу не видит — только функции `app.rate_limit_take` (запросы одного субъекта проверяются по очереди под `pg_advisory_xact_lock`, поэтому одновременные запросы не проходят сверх предела), `app.rate_limit_release` (номер сверяется с видом и субъектом: чужое действие не отпустить), `app.rate_limit_cleanup`; строки старше суток удаляет задача `system.cleanup-rate-limits`. Счёт кодов страницы контрагента (поток Е) может жить в этой же таблице с другим `kind`, но правило «5 неверных подряд — 15 минут» потребует расширить функции (сброс после верного кода, блокировка на время).

Г-1. **Файлы: хранение и блок «Файлы» записи (задача 2.04, #60).** Файлы всех записей — одна таблица `files` (миграции 0036 и 0037), а не свои таблицы у каждого модуля: «Файловому менеджеру» (задача 2.29) нужен один список файлов организации с источником.
    - Модуль кода — `files`: `packages/domain/src/files`, `packages/db/src/files.ts` и `schema/files.ts`, `packages/api/src/modules/files`, `apps/web/src/files`; компонент блока — `FilesBox` (`packages/ui`).
    - Источник файла — вид записи `source_kind` и её номер `source_id` (у «Загружен вручную» номера нет), контрагент записи `contractor_id` — для области «Свои контрагенты» группы «Файловый менеджер» (внешний ключ на контрагентов — вместе с их таблицей, задача 2.05). Модуль с блоком «Файлы» добавляет свой вид в `FILE_SOURCE_KINDS` (`packages/domain`) и строку в `FILE_SOURCES` (`packages/api/src/modules/files/sources.ts`): `resolve` находит запись в транзакции организации с областью своего модуля, говорит, можно ли её менять, и куда писать историю. Пока записей нет, источник один — общие файлы организации (`manual`).
    - Права: видит файлы «Просматривать файлы» в области группы «Файловый менеджер» и только у записи, которую видит; прикрепляет — «Загружать файлы» и право менять запись в её модуле; удаляет свой файл в течение суток без права, любой — с «Удалять файлы». Функция «Файлы в карточках» выключена — 403 `files_off`. Сутки считаются по настоящим часам: время загрузки ставит база (`now()`), а не часы демо-стенда (`FIXED_NOW`).
    - Загрузка мимо API: Vercel не принимает тело запроса больше 4,5 МБ, а файл бывает до 20 МБ. `POST /api/files/uploads` проверяет имя, тип и размер, права и заводит запись `pending`; браузер кладёт файл в хранилище `PUT` по ссылке на 15 минут, в подписи которой размер и тип (другой файл хранилище не примет); `POST /api/files/{id}/complete` проверяет, что файл дошёл и размер тот (`storage.stat`), и показывает файл в записи с историей «Прикреплён файл». Закончить загрузку может только тот, кто начал. Незаконченные загрузки старше суток убирает задача `files.cleanup-pending` (каждый час).
    - Скачивание — подписанная ссылка на 15 минут с именем файла (`GET /api/files/{id}/link`; для ссылок на странице, например в «Истории статусов», — `GET /api/files/{id}/download`, переход на неё). Ссылки на хранилище подписываются по его адресу для браузера `S3_PUBLIC_ENDPOINT` (в Docker — `http://localhost:9000`; пусто — `S3_ENDPOINT`).
    - Удаление — отметка `deleted` с автором и временем, с версией записи («изменено другим»), история «Удалён файл»; сам файл стирается из хранилища после сохранения. Строка остаётся, чтобы ссылка из «Истории статусов» (`status_history.file_id`, ключ на файл своей организации) показывала имя удалённого файла без ссылки. Роль приложения меняет у файла только состояние, контрагента, комментарий и служебные поля (права на столбцы, миграция 0037); вставить можно только свою загрузку `pending`, удалённый файл не меняется, стереть строку можно только у незаконченной загрузки (ограничительные политики).
    - История пишется по каждому файлу («Прикреплён файл», «Удалён файл»): файлы загружаются и проверяются по одному. Строку «Прикреплены файлы: …» на всю пачку, как в прототипе (`services.js`, `bindFiles`), соберёт экран истории записи из подряд идущих `file_attach` одного автора.
    - Защита загрузки (ревью безопасности): ссылка на загрузку живёт 2 минуты (файл, уже показанный в записи, ею не подменить), после загрузки сверяются и размер, и тип; не больше 300 начатых загрузок в час от пользователя (`rate_limits`, вид `file_upload`, 429 `file_upload_limit`); имя с точкой в конце или со знаками смены направления текста — «Неверное имя файла». На VPS поддомен хранилища отдаёт `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox` (docs/migration-vps.md).
    - Для следующих задач: ручная загрузка с контрагентом (2.29) проверяет область и по `files.contractor_id`, а не только по записи-источнику; модуль, который ставит `status_history.file_id`, проверяет, что файл загружен и прикреплён к этой же записи, а «История статусов» показывает файл только с правом «Просматривать файлы».
    - Блок «Файлы» без права «Просматривать файлы» или с выключенными «Файлами в карточках» не показывается (`RecordFiles` при ответе 403 ничего не рисует).
    - Тип файла определяется по расширению; программы, сценарии и веб-страницы не загружаются (docs/deviations.md п. Г-1). Хранилище отдаёт файл вложением с этим типом, поэтому файл не откроется страницей сайта.
    - Пункты приёмки проверяются на странице образцов `/samples` (общие файлы организации): модулей с записями ещё нет. Демо-файлов в наполнении нет — их добавит «Файловый менеджер» (задача 2.29).

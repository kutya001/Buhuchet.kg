# Решения

Журнал решений, принятых при разработке (кроме решений плана и ТЗ). Новое решение — сверху.

## 2026-10-25. Этап 0

1. **Монорепозиторий pnpm + Turborepo, внутренние пакеты без сборки.** Пакеты экспортируют исходники TypeScript; Next.js транспилирует их (`transpilePackages`), worker собирается tsup в один файл, инструменты запускаются через `tsx`. Так не нужно следить за сборкой каждого пакета.
2. **Версии.** Node 22 LTS, TypeScript 5.9 (typescript-eslint ещё не поддерживает TS 7), Next.js 16, React 19, Hono 4 + @hono/zod-openapi 1 (Zod 4), Drizzle ORM 0.45 + drizzle-kit 0.31, Vitest 5, Playwright 1.63, Tailwind CSS 4. Общие версии — в `catalog:` файла `pnpm-workspace.yaml`.
3. **MinIO — сборка сообщества `pgsty/minio`.** Официальные образы MinIO больше не публикуются в Docker Hub и quay.io. Для docker-compose (разработка, CI, VPS) берём закреплённую версию `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` — тот же MinIO. Код от этого не зависит: он говорит только по протоколу S3, поэтому при необходимости MinIO заменяется на Cloudflare R2, Garage или SeaweedFS без правок кода. Вопрос передан треду «Архитектура и план разработки».
4. **Справочники платформы в этапе 0 — разделы refDB.json как JSONB** (`platform_reference`: ключ раздела, содержимое, контрольная сумма, версия, источник). Модуль «Справочники платформы» (поток Д) разложит разделы по своим таблицам и добавит историю загрузок. ГКЭД сразу в своей таблице `gked_items` с поиском pg_trgm.
5. **Наполнение по умолчанию только добавляет.** `pnpm db:seed` не перезаписывает то, что администратор платформы уже поменял; `--update` обновляет изменившиеся разделы (локально, в CI и на стенде после `pnpm spec:sync`). Демо-организация не создаётся при `APP_ENV=production`.
6. **Один маршрут расписания.** Vercel Cron и worker вызывают только `/api/cron/tick` раз в минуту; расписания задач (cron по Бишкеку) и защита от повторов (`scheduler_runs`, первичный ключ job+slot) — в нашем коде и базе. Vercel Cron вызывает GET, worker и cron на VPS — POST, оба с `Authorization: Bearer <CRON_SECRET>`.
7. **Автослияние — свой workflow, squash.** `automerge.yml` сливает PR, когда последние запуски `check`, `docker-e2e`, `pr-policy` зелёные, PR не черновик и без метки `hold`, ветка не отстала от main. Скрипт берётся из main. Встроенное автослияние GitHub требует защиты ветки, которая для закрытых репозиториев доступна не на всех тарифах; если защита включена, оба механизма работают вместе.
8. **Отчёт агентов-ревьюеров — обязательная проверка.** `pr-policy` требует в описании PR раздел «Отчёт ревьюеров» с выводами `spec-reviewer` и `security-reviewer` и падает, если найдено критичное или несоответствие ТЗ.
9. **Сайт не индексируется** (`robots.txt` — Disallow: /, метатег noindex, API отдаёт `X-Robots-Tag: noindex`) до решения о публичных страницах.
10. **Sentry подключается на шаге развёртывания**: переменная `SENTRY_DSN` уже в схеме настроек; SDK добавим вместе с аккаунтом, чтобы не тянуть его без ключа.
11. **RLS включён у каждой таблицы `public`, политики — только для роли `buhuchet_app`.** Таблицы организаций — изоляция по `org_id`; справочники платформы — только чтение; служебные таблицы (запуски задач) — чтение и запись. У остальных ролей политик нет, поэтому даже если на Supabase останется включённым Data API, ключ anon ничего не увидит и не изменит. Тест `rls.test.ts` падает, если у новой таблицы забыли RLS. Роль входа приложения называется `buhuchet_*`, пароль ей задаётся в виде SCRAM-SHA-256 (открытый пароль не попадает в журнал базы), миграции отказываются работать с ролью, у которой есть права владельца таблиц.
12. **PR, который меняет проверки, автослияние или хуки** (`.github/`, `scripts/automerge.mjs`, `scripts/check-pr-policy.mjs`, `scripts/check-protected.mjs`, `scripts/protected-paths.mjs`, `.claude/hooks/`, `.claude/settings.json`), сам не сливается — сливает заказчик: для `pull_request` GitHub берёт workflow из ветки PR, и такой PR мог бы ослабить проверки сам себе. Шаг CI «Применённые миграции и spec/ не тронуты» не пропускает изменение миграций из main и ручную правку spec/ (только `pnpm spec:sync`, которая меняет `spec/SOURCE.json`). Учитываются только проверки GitHub Actions.
13. **`APP_ENV` обязательна; на стенде и рабочем сайте `CRON_SECRET` — от 32 символов и не из `.env.example`.** Сайт проверяет настройки при запуске (`apps/web/instrumentation.ts`), а не при первом запросе: без нужных настроек он не стартует, как и worker; `next build` настроек не требует.
14. **Пароль владельца базы (`DATABASE_ADMIN_URL`) — только у миграций и наполнения**: в docker-compose он есть только у сервиса `migrate`, в Vercel не задаётся.
15. **Заголовки безопасности.** Страницы: `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy`, HSTS (`next.config.ts`, одинаково на Vercel и VPS); API: `secureHeaders` Hono и `Cache-Control: no-store` по умолчанию. Файлы отдаются только вложением по ссылке не дольше 15 минут.
16. **Миграции стенда — `migrate-test.yml`** (`db:migrate`, `db:seed --update`, `storage:init` с `APP_ENV=staging`) только с кода `main`: после автослияния PR, меняющего `packages/db/` или `spec/data/`, его запускает `automerge.mjs` через `workflow_dispatch` (слияние токеном `GITHUB_TOKEN` не запускает `push`), при слиянии человеком — `push`, иначе вручную. База — через пул Supabase в режиме сеанса (у бесплатного проекта прямое подключение только по IPv6). Секреты — секреты репозитория `TEST_*`, только в шагах, которым нужны (Environment в закрытом репозитории — только на платных тарифах GitHub).
17. **Пользователи, сотрудники и роли (задача #3).** Учётная запись (`users`: логин, хеш argon2id, блокировка, «сменить пароль при входе») отдельно от сотрудника (`employees`: ФИО, телефон, роль, «активен»). Один пользователь — одна организация, поэтому `org_id` лежит и в `users` (пусто только у администратора платформы — это проверяет ограничение таблицы): по нему работает обычная изоляция RLS, а сотрудник, роль, права и область ссылаются на пары `(id, org_id)` и не могут указать на запись другой организации. У роли владельца признак `is_owner` (одна на организацию) и все права по правилу домена, без перечня в `role_permissions`. Набор 39 прав и их группы задаёт код (`PERMISSIONS` в `@buhuchet/domain`), названия и описания — справочник `permissions` из refDB; наполнение останавливается, если refDB расходится с кодом. Задачи по расписанию получают список организаций функцией `app.org_ids()` (SECURITY DEFINER, только номера) и обходят их по одной в `withOrgContext`. Блокировок две, и они не снимают друг друга: `users.blocked` ставит администратор платформы, `employees.active = false` — владелец организации; войти нельзя ни при одной из них. Привязка Telegram — отдельная таблица задачи #6, счётчик неверных паролей — задача #5, тема — #13, состояние приветствия и опросника — «Моя организация».
18. **Организация создаётся ролью приложения под RLS** (`createOrganization` в `@buhuchet/db/organizations`): одна транзакция от имени новой организации — роли из шаблонов платформы, владелец с временным паролем, учётная политика по умолчанию. Так же её будет создавать Админка. До Админки — служебные команды `pnpm db:create-org` и `pnpm db:create-admin` (администратору платформы нужен владелец схемы, потому что у него нет организации); временный пароль печатается один раз. Демо-сотрудники входят паролем из `DEMO_PASSWORD`; без этой настройки (так по умолчанию на стенде) войти в демо-организацию нельзя.
19. **История изменений и версия записи (задача #4).** Одна общая таблица `audit_log` для всех записей организации («одна таблица истории на всё», как в «Основных паттернах»): вид записи и её номер, действие, изменённые поля «было → стало» (JSONB), причина, контрагент (для истории в карточке контрагента), автор и время. Организация, автор и время подставляются базой из контекста транзакции (`app.org_id`, `app.user_id`, `now()`); ограничивающая политика вставки не даёт записать другого автора, другое время или пользователя чужой организации (автором может быть только пользователь этой организации или администратор платформы — проверка `app.history_actor_allowed`, SECURITY DEFINER); без пользователя автор — «Система». Записи только добавляются: у роли приложения нет прав UPDATE и DELETE на таблицу. Значения секретных полей (по списку и по окончанию имени Hash, Token, Secret) не пишутся — только факт изменения. Правка записи с версией (`updateWithHistory`) принимает только столбцы таблицы без служебных, блокирует строку до конца транзакции (`SELECT … FOR UPDATE`) и сверяет версию: устаревшая → `RecordChangedError` → 409 `record_changed`; так вторая из одновременных правок ждёт первую и получает предупреждение, а не затирает её. Условие области «Свои контрагенты» передаётся в тот же запрос (`where`), запись вне области — 404, как чужая. Ошибки запросов к базе пишутся в журнал без значений параметров. Пока не сделано и решается вместе с модулями: история платформы (справочники, администратор без организации — столбец `org_id` обязателен), автор «Контрагент (по ссылке)» и пометка источника («Из Excel», «по опроснику»), история статусов с откатом (#17).
20. **Вход и сеансы (задача #5).** Сеанс — 32 случайных байта в cookie `__Host-bh_session` (HttpOnly, Secure, SameSite=Lax, Path=/; локально и в сквозных тестах по http — `bh_session` без Secure), в таблице `sessions` — только SHA-256 токена. Сеанс живёт 30 дней с последнего обращения (docs/deviations.md, п. 5) и продлевается не чаще раза в час (тогда cookie выдаётся заново). Вход, проверка cookie и выход идут до того, как известна организация, поэтому они — узкие функции `app.auth_*` (SECURITY DEFINER, только для роли приложения), а не чтение таблиц в обход RLS. Пять неверных паролей подряд закрывают вход на 15 минут. Счёт ведётся по набранному логину, есть такой логин или нет (таблица `login_attempts` без организации; роль приложения её не видит, только функции `app.auth_login_*`), поэтому «вход закрыт» одинаков для любого логина; через час после последней попытки счёт забывается, такие строки каждые 10 минут удаляет задача `auth.cleanup-login-attempts` (на скорость подбора срок не влияет: её задают 5 попыток на 15 минут, а таблица не растёт от выдуманных логинов дольше часа). Попытка занимается в базе до проверки пароля (`app.auth_login_attempt`, строка логина блокируется до конца функции), а пока вход закрыт, пароль не проверяется вовсе: одновременные запросы не проверят больше пяти паролей. Верный пароль, смена пароля, код из Telegram и временный пароль снимают счёт. Неверный текущий пароль при смене пароля считается так же (иначе украденный сеанс позволял бы подбирать пароль без ограничения), и пятый такой ответ — тоже «вход закрыт». Выход удаляет сеанс, смена пароля — все остальные сеансы пользователя, а текущему выдаёт новый токен: старая cookie не действует нигде. Блокировка сотрудника, учётной записи или организации (`organizations.status`; причина — необязательная пометка администратора) закрывает и уже открытые сеансы при следующем запросе; тексты — как в прототипе (сотрудник, которого заблокировал и владелец, и администратор платформы, видит «Обратитесь к владельцу организации»); при входе о блокировке сообщается только после верного пароля. Общий слой API: все пути, кроме открытых (`/api/health`, `/api/cron/tick`, `/api/openapi.json`, вход и выход), требуют сеанс (401); с временным паролем доступны только «кто я» и смена пароля (403 `password_change_required`); для сотрудника права и области загружаются в контексте его организации; право метода — `requirePermission` в `createRoute`; организация метода — только из сеанса (`orgContextOf`). Изменяющие запросы (всё, кроме GET, HEAD, OPTIONS) принимаются только с заголовком Origin нашего адреса — `APP_BASE_URL` или Host запроса; заголовкам прокси (X-Forwarded-Host) не верим; без Origin пропускаются только вызовы планировщика с секретом. Тело запроса API — не больше 1 МиБ (файлы идут в хранилище мимо API). Cookie с `Secure` и `__Host-` — на стенде, рабочем сайте и любом сайте по https; на стенде и рабочем сайте `APP_BASE_URL` обязателен и только https (сайт без него не стартует). Пока не сделано: лимит попыток входа с одного IP (нужен до рабочего сайта: без него выдуманные логины наполняют `login_attempts`, а один пароль можно пробовать на многих логинах), запрет менять служебные столбцы (`organizations.status`, `users.blocked`, счётчик паролей) обычными методами на уровне базы — методы «Моя организация» и «Сотрудники» (#7, #8) собирают правку из явного списка полей, а меняет их только Админка (#18). Администратор платформы входит без организации и прав в организациях не имеет. Неизвестный логин и неверный пароль — одно сообщение «Неверный логин или пароль» и одно время ответа (docs/deviations.md, п. 4, решение Б).
21. **Telegram и «Забыли пароль?» (задача #6).** Привязка — отдельная таблица `telegram_links` (у пользователя один чат, один чат — у нескольких логинов, тогда в сообщениях первой строкой идёт организация). Ссылка «Скопировать ссылку» — `t.me/<TELEGRAM_BOT_USERNAME>?start=<токен>`: 32 случайных байта, в базе только SHA-256 (`telegram_link_tokens`), действует 15 минут, у пользователя — только последняя; использованная остаётся с отметкой, чтобы повтор того же сообщения Telegram не ответил «ссылка недействительна». Если вместо прежнего привязан другой чат, бот пишет об этом в прежний (`tgRelinked`), при отвязке — в отвязанный (`tgUnlinked`): привязка — способ восстановить пароль, и чужая замена по украденному сеансу не должна пройти незаметно. Вебхук `/api/telegram/webhook` открыт без входа и без Origin, но принимается только с секретом `TELEGRAM_WEBHOOK_SECRET` в заголовке `X-Telegram-Bot-Api-Secret-Token`, проверка — до разбора тела; без бота (нет токена) метода как будто нет (404). Бот отвечает только на текст в личном чате; на остальное — 200 без ответа, чтобы Telegram не повторял доставку. Вебхук сайт ставит сам: задача по расписанию `telegram.register-webhook` каждые 10 минут вызывает `setWebhook` с адресом `<APP_BASE_URL>/api/telegram/webhook` и секретом, если бот задан и адрес по https (повтор с теми же данными ничего не меняет, смена секрета подхватывается сама); токен — только в окружении (docs/deviations.md, п. 14). «Забыли пароль?» для любого логина отвечает одинаково и не быстрее 1,5 с (`RESET_RESPONSE_FLOOR_MS`), чтобы ни текстом, ни временем не было видно, есть ли логин и привязан ли Telegram (docs/deviations.md, п. 4, решение Б); код уходит, только если логин есть, не заблокирован, Telegram привязан и лимиты позволяют. Код — 6 случайных цифр, в базе — хеш argon2id (`password_reset_codes`), 10 минут, не больше 3 в час на логин, новый код отменяет прежний; лимиты проверяются функцией `app.auth_reset_status` до того, как считать хеш (запросы сверх лимита не нагружают сервер), и ещё раз под блокировкой строки пользователя в `app.auth_reset_request` (одновременные запросы их не превысят). Запрос, на который Telegram не принял сообщение, тоже считается: код записывается до отправки. ТЗ не ограничивает число вводов кода, но без ограничения 6 цифр перебираются за 10 минут, поэтому ввод занимается до проверки, как попытка входа (`app.auth_reset_attempt`): после 5 неверных код не действует; после 10 неверных за 24 часа коды не присылаются и не принимаются 24 часа после последнего кода (иначе 15 вариантов в час без конца — около 1 % за месяц на учётную запись; docs/deviations.md, п. 9). Текст ошибки всегда один — «Код неверный или истёк», и для неизвестного или заблокированного логина тоже. Верный код задаёт новый пароль, закрывает все сеансы и снимает блокировку входа после неверных паролей; сеанс не создаётся — войти нужно новым паролем, как в прототипе. Ожидающий код отменяется (`app.auth_reset_revoke`), когда пароль сменили в профиле или сбросили временным, когда Telegram отвязали или заменили другим чатом: код, отправленный раньше, пароль уже не задаст. Код, ответы бота и служебные сообщения уходят сразу через переходник `telegram` (ответа Telegram ждём не дольше 10 с, кода — 1 с, чтобы медленный Telegram не выдал по времени, что логин есть), мимо очереди (очередь и журнал отправок — поток Б, docs/deviations.md, п. 12); ошибка Telegram пишется в журнал сервера без текста сообщения. Бот сообщает о каждой смене пароля: по коду и в профиле — `tgPassChanged`, сброс временным паролем — `tgPassReset` с тем, кто сбросил. Сброс временным паролем: сотрудник с правом «Сотрудники и роли» (по умолчанию только владелец) — любому сотруднику, кроме владельца (`POST /api/staff/{id}/password-reset`, как в прототипе; docs/deviations.md, п. 11); администратор платформы — любому пользователю организации (`POST /api/admin/users/{id}/password-reset`, действует в контексте её организации и пишет в её историю; учётную запись он находит функцией `app.admin_find_user`, которая отвечает только администратору). Временный пароль показывается один раз, в историю пишется только факт смены. Шаги без входа и без организации — функции `app.telegram_*`, `app.auth_reset_*`, `app.admin_find_user` (миграция 0011, SECURITY DEFINER, только для роли приложения); изменение от имени пользователя — только для `app.current_user_id()` в его `withOrgContext`, с историей в той же транзакции. Таблицы `telegram_links`, `telegram_link_tokens`, `password_reset_codes` роль приложения только читает (под RLS), а меняет — только этими функциями: ошибка в коде не обнулит попытки и не перепривяжет чужой Telegram. Будущий предел неверных попыток с одного IP должен покрывать и `/api/auth/password-reset*`: пачка одновременных запросов на один логин ещё успевает разово посчитать argon2 до записи кода. Пароль для привязки Telegram не спрашивается, сброс пароля Telegram не отвязывает — как в прототипе, решение заказчика (docs/deviations.md, п. 13). Демо-сотрудникам Telegram не привязывается: выдуманный chat_id мог бы оказаться чужим человеком (docs/deviations.md, п. 10).
22. **Сотрудники и роли (задача #7).** Правило галочек роли — одна функция домена для формы (#18) и сервера: `rolePermissionLock` повторяет `roleLock` прототипа и сверена с ним на ролях demoDB (702 ответа, фикстура `packages/domain/src/roles/__fixtures__/role-locks.json`, скрипт `packages/domain/scripts/oracle-roles.mjs`); `roleChangeProblem` проверяет сохранённый набор: добавленное право — полностью («Сначала дайте просмотр» по новому набору, право только владельца, «выдаёт только владелец», своя роль), снятое не держит (право группы без просмотра всё равно не действует, а прототип оставляет его в роли). Роль владельца и свою роль (не владельцу) сервер не меняет вовсе; роль с правами «выдаёт только владелец» меняет, удаляет, назначает и снимает только владелец, и только он сбрасывает пароль, блокирует и разблокирует её носителей. Не владелец не выдаёт больше, чем есть у него (`roleWithinRights`): правка роли сравнивает действующие права и область до и после (в том числе ожившие с возвращённым просмотром группы), а роль шире своей он не назначает новому сотруднику и при смене роли, не сбрасывает пароль, не блокирует и не разблокирует её носителей (docs/deviations.md, п. 15). Решение о сотруднике читает его роль с блокировкой строки на чтение (`roleAccess`, FOR SHARE), а правка роли блокирует её на запись (`lockRole`), поэтому решение не опирается на права, которые в ту же секунду меняют; сброс пароля блокирует и самого сотрудника. Сохранение роли — одна правка с версией: изменения прав и области (только переданные группы) пишутся в историю роли полями `permissions` и `scopes` «было → стало», смена роли сотрудника — ещё и названиями ролей (`roleName`), чтобы история читалась и после удаления роли. Права загружаются при каждом запросе, поэтому новая роль и новые права действуют сразу; блокировка ещё и удаляет сеансы сотрудника в той же транзакции. Логин уникален на всей платформе: «Такой логин уже занят на платформе» (как в прототипе) видят только сотрудники с правом «Сотрудники и роли» при создании сотрудника — это ответ ограничения уникальности базы, чужие учётные записи RLS не показывает. Временный пароль нового сотрудника задаёт владелец (от 8 символов) или сервер (docs/deviations.md, п. 17); в историю идёт только факт создания с ФИО, телефоном и ролью. Удаляется только роль без сотрудников (и заблокированных) и не роль новых сотрудников; если её назначили в ту же минуту, удаление останавливает внешний ключ. Отказ по правилу внутри транзакции — `apiFail` (`packages/api/src/errors.ts`): транзакция откатывается, ответ в общем формате. Счёт, реквизиты для переводов (видны самому сотруднику, владельцу и главному бухгалтеру по ТЗ, а в прототипе — тем, у кого «Сотрудники и роли»: расхождение запишем с задачей о реквизитах), уровень знаний и число контрагентов и отчётов сотрудника добавят их модули; передача контрагентов при блокировке — вместе с контрагентами (поток А).

24. **Локализация (задача #9).** Словарь текстов интерфейса — таблица `ui_texts` (язык, ключ, текст, раздел, кто завёл и кто поправил в Админке, время, версия; ключ — пара «язык + ключ»), общая для всех организаций: роль приложения только читает (RLS), меняет администратор платформы (экран «Локализация» и загрузка из Excel — поток Д). Язык сейчас один — русский (`UI_LANGUAGES`); столбец языка закладывает другие, непереведённые тексты тогда возьмутся из русского. Наполнение — раздел `localization` refDB.json (тексты прототипа) и тексты экранов продукта `UI_TEXTS` (`@buhuchet/domain`): ключ из обоих мест берётся из refDB.json, тест следит, чтобы тексты совпадали. `db:seed --update` обновляет только тексты из наполнения: поправленный в Админке (`updated_by` задан) не затирается. Метод `GET /api/l10n` открыт без входа (словарь нужен на странице входа): тексты базы поверх `UI_TEXTS`, поэтому ключ, выложенный с новым кодом раньше наполнения, всё равно показывается; версия словаря — в ETag, браузер перепроверяет его (`no-cache`) и получает 304, пока словарь тот же. API держит словарь в памяти и не чаще раза в секунду сверяет его с отметкой базы (число текстов и хеш пар «ключ — текст»): перечитывает, только когда она изменилась, — так и текст, поправленный прямо в таблице, виден со следующего обновления страницы. Роль приложения только читает словарь: права на запись забраны (миграция 0017), RLS разрешает только чтение; правку из Админки сделает узкая функция для администратора платформы. База недоступна — отдаются тексты `UI_TEXTS` без кэширования, чтобы страница (в том числе «здоровье») всё равно показалась. Первый показ без мигания: корневой макет сайта берёт словарь на сервере тем же методом API в том же процессе (`apps/web/src/l10n/server.ts`), страница приходит уже с текстами, экраны берут их хуком `useT()`, серверные компоненты — `getT()`; ключ проверяется типом (`UiTextKey`). Строки с русскими буквами в коде `apps/web` и `packages/ui` запрещает ESLint (`no-restricted-syntax`), правило проверяет тест. Пока не сделано, придёт со своими задачами: сообщения ответов API (ошибки) — в коде сервера; экран показывает их через `useErrorText()` из словаря по коду (`err.<код>`), а текст ответа — только если ключа нет, ключи `err.*` заводятся вместе с экранами; раздел `localization` пока копируется и в `platform_reference` (наполнение этапа 0) — источник словаря только `ui_texts`, копия уйдёт, когда «Справочники платформы» разложат разделы по таблицам; тексты сообщений Telegram и значения справочников переводятся, когда языков станет больше (ТЗ); список языков и «сколько строк переведено» — с экраном «Локализация».

Кнопка «Назад» телефона закрывает открытое окно, а не уходит со страницы (`OverlayHistory` и хук `useBackClose` в `packages/ui/src/back-close.ts`, как `ovOpen` и `ovClosed` прототипа): открытое окно кладёт в историю запись-заглушку с тем же адресом (состояние роутера Next копируется, поэтому он её не замечает); «Назад» снимает заглушку и закрывает верхнее окно; закрыли кнопкой, жестом, касанием вне окна или Esc — заглушка снимается `history.back()`; переход из окна (выбор модуля, профиль организации, выход) идёт с заменой записи (`replace`), заглушку заменяет новый адрес, и «Назад» после перехода ведёт на прежнюю страницу, а не к панели. Окна задачи #12 используют тот же хук. Всплывающее окошко (`Popover`) заглушку не кладёт: «Назад» закрывает его, и переход идёт как обычно (`closePop` прототипа). Пока открыто окно, панель или всплывающее окошко (атрибут `data-overlay`), вкладки свайпом не листаются. Правила жестов — чистые функции `packages/ui/src/gestures.ts` (направление по первым 10 px, скорость пальца за последние 90 мс, рывок от 0,5 px/мс, пороги, сопротивление 0,25, время завершения 120–320 мс по скорости пальца; числа из `ui/swipes.js` прототипа); протяжка вниз — хук `useSwipeDown` (панель «Меню», всплывающие окошки `Popover`, потом окна #12); листание вкладок — `TabPager` вокруг экрана модуля. Чтобы соседняя вкладка въезжала за пальцем, экран любой вкладки рисуется из одного места — реестра экранов `apps/web/src/screens/module-screen.tsx` (`ModuleScreen`): его же рисует страница маршрута, поэтому экран модуля регистрируется там, а не отдельной папкой маршрута, как предполагало решение 25. Адрес после свайпа меняется с заменой записи, как в прототипе (п. 25 расхождений); прокрутка каждой вкладки запоминается, пока открыта страница. Поиск на телефоне свёрнут в значок и раскрывается на всю ширину верхней панели; «клавиатура открыта» — фокус в текстовом поле на ширине телефона (как прототип), тогда нижняя панель и «+» скрыты. Вкладки карточки записи «N из M ▾» — общий компонент `CardTabs`, подключится с окнами (#12). Сквозные тесты жестов (`e2e/phone.spec.ts`): медленные протяжки — настоящими касаниями через протокол отладки Chromium, рывки — событиями касания на самой странице, потому что без экрана Chromium доставляет касания протокола примерно раз в 50 мс и рывок выходит медленным. Пока не сделано: «Мой профиль» в панели (#13), точка «Начните с Базы знаний» и счётчики на модулях (с экранами модулей), листание вкладок окна (#12).
27. **Окна, уведомления и пустые состояния (задача #12).** Общие компоненты в `packages/ui`: окно `Modal` (вид `card` — карточка, `form` — форма, `message` — подтверждение без «На весь экран»; ширина 580/780/1100 px; вкладки карточки — проп `tabs`, ряд закреплён вверху содержимого и листается свайпом), `ConfirmDialog`, уведомления `ToastProvider` + `useToast()`, `EmptyState` и `NothingFound`. Окна рисуются в `document.body` (порталом), поэтому сдвиг рабочей области при свайпе их не задевает; тексты и выбор «На весь экран» даёт `WindowProvider` оболочки. Выбор «На весь экран» хранится в cookie `bh_max` (`card`, `form`), как остальной выбор на устройстве (п. 25); окно поверх другого разворачивается само по себе. Форма с несохранёнными изменениями (`dirty`) на протяжку вниз и «Назад» спрашивает «Закрыть без сохранения?» — окно при этом остаётся в истории (`useBackClose` принимает `false` от закрытия); крестик, Esc и касание фона закрывают сразу, как в прототипе. Выход спрашивает «Выйти без сохранения?», только если в открытой форме есть несохранённые изменения (`useWindows().hasUnsavedForm()`; прототип спрашивал при любой открытой форме; решение заказчика 26.10.2026 — по ТЗ, п. 27 расхождений). Пока окно тянут вниз, светлеет только фон: он отдельным слоем под окном. Красный счётчик модуля и вкладки — цвета опасной кнопки (п. 26 расхождений). Помощь «?» — окно «Базы знаний» о модуле (kbHelp прототипа без статьи); «Показать экран» придёт с «Показать как» (поток Г), профиль организации окном — с экранами «Моей организации» (#19). Заглушка модуля подтверждает выбор в «+ Добавить» уведомлением. Пустые состояния первого входа и «Ничего не найдено» подключат экраны списков (#14–#16) и модулей; там же — сквозной тест пункта «Новая организация видит пустые модули…». Пока не сделано, придёт со своими задачами: поля формы (подпись, обязательность, подсказка, ошибка — `fld` и `setErr` прототипа) и компоновка форм на телефоне до 600 px (короткие поля по два в строку, прототип ui/mobile-pack.js `packForm`) — с первыми формами (#13); пары «подпись — значение» карточки просмотра по два в строку (`packKv`) — с карточкой сотрудника (#18); таблицы внутри развёрнутого окна во всю ширину и высоту с закреплённым заголовком и итогами внизу (прототип `.modal.max .gscroll`, `.modal.max .mx`) — с общим списком (#14) и карточкой сотрудника (#18), там же — шаг «На весь экран» и листание вкладок развёрнутой карточки в сквозном тесте пункта 1; сквозные тесты «Закрыть без сохранения?» (протяжка и «Назад») и «Выйти без сохранения?» — с первой формой (#13), пока правила проверены на `closesAtOnce` и `WindowStack`.
28. **Вход и «Мой профиль» (задача #13).** Страница `/login` — одна карточка с шагами (`apps/web/src/auth/login-screen.tsx`): вход → «Забыли пароль?» (логин → код из Telegram и новый пароль) → снова вход с подставленным логином; вход с временным паролем → «Смените временный пароль» (только что введённый временный пароль второй раз не спрашивается, после перезагрузки страницы — спрашивается; страницы за входом ведут обратно сюда) → «Привяжите Telegram», если он не привязан и бот подключён к платформе. Привязать Telegram предлагается после смены временного пароля, а не при каждом входе без Telegram: каждая настоящая учётная запись начинается с временного пароля, дальше напоминает предупреждение в «Моём профиле»; «Позже» ведёт в программу. Подсказки «Демо: логины …» прототипа на странице входа нет — она только для прототипа. Неверный логин или пароль — ошибка под паролем с общим предупреждением о блокировке (п. 4 расхождений, дополнение), блокировка сотрудника или организации — под логином. Формы — React Hook Form со схемами `LoginForm`, `PasswordResetLoginForm`, `PasswordResetCodeForm`, `ChangePasswordForm` из `@buhuchet/shared`: сообщения схем — ключи словаря (`auth.err.*`, числа правил подставляет `fieldErrorText`), ошибка ответа API ставится полю с типом `server` текстом `useErrorText()`; поля регистрируются до разметки в порядке экрана, чтобы фокус вставал на первое неверное поле. Запросы — `callApi` (`apps/web/src/api-client.ts`): данные или ошибка `{ code, message }`, сбой сети — код `network`. Поля форм — `Field`, `FormGrid`, `KeyValues`, `Box`, `Note`, `Pill` и `inputClass` в `packages/ui/src/form.tsx` (`fld`, `setErr`, `.kv`, `.box`, `.note`, `.pill` прототипа); на телефоне до 600 px `FormGrid` и `KeyValues` раскладываются как `packForm` и `packKv` прототипа (`ui/mobile-pack.js`): два коротких поля — в строку, длинное — во всю ширину, распорки скрыты; ширину подписей и значений `useFormPack` меряет на холсте, правила — чистые функции `form-pack.ts` с тестами. «Мой профиль» — окно-карточка (`apps/web/src/profile/profile-window.tsx`) из левой панели на ПК и из панели «Меню» на телефоне (с инициалами и ФИО): «Основное» (ФИО, логин, телефон в виде «+996 555 100 200» — `formatPhone` по кодам стран справочника, роль), Telegram (привязан — имя и «Отвязать»; не привязан — предупреждение, ссылка и «Скопировать ссылку»; привязку экран узнаёт, спрашивая «кто я» раз в 3 секунды), «Личные настройки» (тема применяется сразу и хранится в cookie `bh_theme`) и «Смена пароля»; «Мои реквизиты», уровень знаний и уведомления придут со своими задачами. Ссылки привязки запрашиваются по одной: каждая новая отменяет прежние, и на экране должна остаться выданная последней. Карточка с несохранёнными изменениями (`dirty`) теперь тоже спрашивает «Закрыть без сохранения?» на протяжку вниз и «Назад» и учитывается при выходе (раньше — только форма, п. 27); у профиля `dirty` — пока в «Смене пароля» что-то введено. Окно закрывает панели, и нажать «Выйти» при открытом окне нельзя; правило «Выйти без сохранения?» остаётся на случай выхода не из панели и проверяется сквозным тестом нажатием скрытой кнопки. Бот-подделка сквозных тестов `e2e/fake-telegram.ts` (порт 8091, запускает Playwright) отвечает как Bot API на `sendMessage` и `setWebhook` и отдаёт тестам отправленные сообщения; сайт говорит с ней через `TELEGRAM_API_BASE` (`.env.example`; из Docker — `host.docker.internal`, `extra_hosts: host-gateway`). В `.env.example` — поддельные токен, имя бота и секрет вебхука, поэтому локально и в CI бот подключён; на стенде и рабочем сайте `TELEGRAM_API_BASE` запрещена схемой настроек, а секрет вебхука — свой, от 32 символов.

# Развёртывание: стенд и рабочий сайт

Этап 0 проверен локально и в CI (Docker). Аккаунты оформляет заказчик; ключи и пароли задаются только в настройках окружения (Vercel, GitHub), не в чат и не в репозиторий.

## Схема
- Ветка `main` — тестовый стенд `test.buhuchet.kg`: сюда автослиянием приходят все PR. Ветка `production` — рабочий сайт `buhuchet.kg`: обновляется только по команде заказчика «выпускай».
- Из одного репозитория два проекта Vercel: `buhuchet-kg` — стенд (Production Branch = `main`, домен `test.buhuchet.kg`, тестовая база) и `buhuchet` (Production Branch = `production`, домен `buhuchet.kg`, рабочая база). Два проекта, потому что Vercel Cron вызывает только production-выпуск проекта, а `/api/cron/tick` нужен и на стенде.
- Supabase: бесплатный проект `buhuchet-test` (стенд, eu-west-1 — Ирландия) сейчас, рабочий — Pro-проект `buhuchet-prod` во Frankfurt (eu-central-1), как в ТЗ (docs/deviations.md, п. 1; раздел «Рабочий сайт»).

## Supabase: создание проекта
- **Enable Data API — выключить**, **Automatically expose new tables — выключить** (supabase-js и REST Supabase не используются, браузер к базе не обращается); **Enable automatic RLS — не включать** (RLS включают наши миграции: этот триггер есть только в Supabase, его нет локально и на VPS); **Connect GitHub — не подключать** (миграции применяет наш CI).
- Если Data API уже включён: Project Settings → Data API → выключить (или убрать `public` из открытых схем). Даже без этого строки не видны: у ролей `anon` и `authenticated` нет политик RLS (docs/decisions.md, п. 11).
- Регион: у бесплатного проекта выбирается только часть света (**Europe**), город назначает Supabase — он виден в Project Settings → General. Функции Vercel ставятся в тот же регион — в настройках каждого проекта (Settings → Functions → Function Region): стенд `buhuchet-kg` — `dub1` (eu-west-1), рабочий сайт `buhuchet` — `fra1` (рабочий Pro-проект Supabase — **Frankfurt**, регион проекта потом не меняется). `vercel.json` один на оба проекта, поэтому `regions` в нём нет — он перекрыл бы обе настройки (проверяет `apps/web/src/vercel-config.test.ts`).
- Storage → создать закрытую корзину `buhuchet` (Public — выключено); Storage → S3 Connection → создать ключи S3 (Access key ID и Secret).

## Vercel: проект стенда `buhuchet-kg`
- Import Git Repository → `kutya001/Buhuchet.kg`; Framework Preset — Next.js; **Root Directory — `apps/web`**; «Include files outside of the Root Directory in the Build Step» — включено (по умолчанию).
- Install Command и Build Command — по умолчанию (pnpm ставит весь монорепозиторий, `next build` сам транспилирует внутренние пакеты). Output Directory — по умолчанию.
- Node.js 22 Vercel берёт из `engines` в `apps/web/package.json` (настройка Node.js Version в проекте при этом не действует; без `engines` Vercel взял бы версию из настроек, 24.x, и `pnpm install` остановился бы на `engines` корневого `package.json`). Settings → Git → Production Branch — `main`.
- К репозиторию подключены только проекты из схемы выше: проект, который собирает репозиторий из корня (без Root Directory), падает на каждом PR с «No Next.js version detected» — его отключают (Settings → Git → Disconnect).
- Сборка сайта (`apps/web` → `build`) сначала собирает демо-версию `public/demo.html` из `spec/prototype` командой прототипа `python3 build.py --demo … --site=/ --lead=/#lead` (`scripts/build-demo.mjs`, задача #165): в образе сборки Vercel Python 3 есть, в Dockerfile он ставится (`apk add python3`). Демо-версия обновляется вместе со `spec/` при каждом `pnpm spec:sync`; демо-картинки лендинга после `spec:sync` пересобирает `pnpm landing:data` — тест `apps/web` сверяет их с `spec/` (числа полосы цифр и коды стран лендинг берёт из справочников в базе).
- Расписание задаётся в `apps/web/vercel.json` (`/api/cron/tick` раз в минуту), регион функций — в настройках проекта (см. выше). Расписание раз в минуту требует тарифа Vercel Pro — команда проектов на Pro; проверено 25.10.2026 по журналам Vercel: `/api/cron/tick` вызывается раз в минуту.
- Settings → Domains → `test.buhuchet.kg`. Серверы имён `buhuchet.kg` в кабинете cctld.kg — серверы Vercel (`ns1.vercel-dns.com`, `ns2.vercel-dns.com`; решение заказчика 30.10.2026, ТЗ «Домен buhuchet.kg»): записи DNS, в том числе поддомены, ведутся в Vercel → Domains → `buhuchet.kg`, а домены, привязанные к проектам, Vercel обслуживает сам.

## Переменные окружения
Vercel → проект → Settings → Environment Variables, окружение Production (для `buhuchet-kg` это стенд). Полный список с пояснениями — `.env.example`.
- `APP_ENV` = `staging` (у рабочего сайта — `production`); `APP_BASE_URL` = `https://test.buhuchet.kg`.
- `DATABASE_URL` — роль приложения через пул Supabase в режиме транзакций (Connect → Transaction pooler, порт 6543), пользователь `buhuchet_web.<ref проекта>`, свой новый пароль (не пароль `postgres`). Роль с этим паролем создаёт `pnpm db:migrate`.
- `DATABASE_CA_CERT` (необязательно, рекомендуется) — корневой сертификат Supabase: Database → Settings → SSL Configuration → Download certificate, содержимое файла целиком (можно одной строкой с `\n`). С ним соединение проверяет сертификат и имя сервера базы (как `sslmode=verify-full`), без него — только шифрует (`sslmode=require`). Сначала задать на стенде и проверить вход, потом — на рабочем сайте.
- `S3_ENDPOINT` = `https://<ref проекта>.storage.supabase.co/storage/v1/s3`, `S3_REGION` = регион проекта (у стенда — `eu-west-1`), `S3_BUCKET` = `buhuchet`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE` = `true`.
- `CRON_SECRET` — случайная строка от 32 символов (Vercel Cron передаёт её сам; примерная из `.env.example` на стенде и рабочем сайте не принимается).
- Бот: `TELEGRAM_BOT_TOKEN` (от BotFather), `TELEGRAM_WEBHOOK_SECRET` (своя случайная строка от 32 символов: латиница, цифры, `_` и `-` — другие символы Telegram не принимает; значения из `.env.example` стенд и рабочий сайт не примут) и `TELEGRAM_BOT_USERNAME` (имя бота без «@») — только вместе, токен и секрет с отметкой Sensitive. `TELEGRAM_API_BASE` (адрес бота-подделки для тестов) на стенде и рабочем сайте не задаётся. У стенда и рабочего сайта боты разные: у бота один вебхук. В окружении Preview переменные бота не задаются (или там свой бот): иначе превью из непроверенной ветки перехватит вебхук общего бота. Позже: `SENTRY_DSN` (при подключении Sentry вычищать из записей запросов адреса `api.telegram.org/bot…` — в них токен). На стенде можно `FIXED_NOW` для демо-даты.
- Вебхук ручного шага не требует: когда переменные бота заданы и сайт пересобран (Deployments → Redeploy), задача по расписанию `telegram.register-webhook` в течение 10 минут сообщает Telegram адрес `<APP_BASE_URL>/api/telegram/webhook` и секрет (метод Bot API `setWebhook`, `allowed_updates`: `message`, `callback_query`) и повторяет это каждые 10 минут — так подхватывается и смена секрета. Задача есть, только если бот задан и `APP_BASE_URL` по https. Ошибка регистрации видна в журнале и в `scheduler_runs`.
- `DATABASE_ADMIN_URL` в Vercel **не задаётся**: пароль владельца базы есть только у миграций в GitHub Actions.
- Без обязательных переменных сайт не стартует и пишет в журнал, чего не хватает (`apps/web/instrumentation.ts`).

## GitHub (Settings репозитория)
- **Secrets and variables → Actions → New repository secret** — секреты стенда с приставкой `TEST_`: `TEST_DATABASE_ADMIN_URL` — пользователь `postgres.<ref проекта>` через пул в режиме сеанса (Connect → Session pooler, порт 5432; прямое подключение у бесплатного проекта только по IPv6, а у GitHub Actions его нет), `TEST_DATABASE_URL` — та же строка, что `DATABASE_URL` в Vercel, `TEST_S3_ENDPOINT`, `TEST_S3_REGION`, `TEST_S3_ACCESS_KEY_ID`, `TEST_S3_SECRET_ACCESS_KEY` — те же, что в Vercel, и необязательные `TEST_DEMO_PASSWORD` — пароль демо-сотрудников стенда (своя строка от 12 символов), `TEST_ADMIN_LOGIN` и `TEST_ADMIN_PASSWORD` — администратор платформы стенда (вместе; пароль от 8 символов, временный). Их читает только `.github/workflows/migrate-test.yml` и только в шагах миграций, наполнения и корзины; пока нет обязательных (все, кроме `TEST_DEMO_PASSWORD`, `TEST_ADMIN_LOGIN` и `TEST_ADMIN_PASSWORD`), он пропускает работу. Секреты рабочего сайта — не здесь, а в окружении `production` (раздел «Рабочий сайт»).
  - Почему не Environment: секреты Environment и ограничение их веткой `main` в закрытом репозитории есть только на платных тарифах GitHub. Секреты репозитория видит workflow из любой ветки, поэтому в них — только тестовый стенд с демо-данными; если тариф GitHub Pro или выше, секреты переносятся в Environment `test` с ограничением веткой `main`. С 30.10.2026 репозиторий открыт — в открытом репозитории Environment с секретами, ограничением веткой и одобрением (Required reviewers) есть на любом тарифе; им пользуется рабочий сайт (раздел «Рабочий сайт»).
- **General → Pull Requests**: включить «Allow auto-merge» и «Automatically delete head branches».
- **Branches → Branch protection rule (или Ruleset) для `main`** (если тариф позволяет для закрытого репозитория): Require a pull request, Require status checks `check`, `docker-e2e`, `pr-policy`, запрет force-push. Без защиты автослияние всё равно работает через `.github/workflows/automerge.yml`, а прямой push в main запрещает хук Claude Code.

## Первая организация и администратор платформы
- Администратора платформы стенда создаёт `pnpm db:seed`, если заданы `PLATFORM_ADMIN_LOGIN` и `PLATFORM_ADMIN_PASSWORD` (на рабочем сайте не задаются: первого администратора рабочего сайта создаёт выпуск с отметкой «Создать администратора», раздел «Рабочий сайт»): на стенде — из секретов `TEST_ADMIN_LOGIN` и `TEST_ADMIN_PASSWORD` при следующем запуске `migrate-test.yml`. Пароль временный — при первом входе сайт попросит задать свой; уже созданного администратора наполнение не трогает (пароль, который он сменил, не возвращается), а логин, занятый сотрудником организации, останавливает наполнение. Пароль в журнал не печатается. Смена `TEST_ADMIN_LOGIN` создаёт второго администратора (прежний остаётся).
- Забытый пароль администратора стенда: в секрет `TEST_ADMIN_PASSWORD` записать новый временный пароль (от 8 символов), затем Actions → Migrate test → Run workflow (ветка `main`) с отметкой «Сбросить пароль администратора платформы». Наполнение (`pnpm db:seed --update --reset-admin-password`) снова делает пароль администратора `TEST_ADMIN_LOGIN` временным из секрета, завершает его сеансы и снимает блокировку входа после неверных паролей, а бот сообщает о сбросе в привязанный Telegram; при входе сайт попросит задать свой пароль. Без отметки (и при запуске после слияния PR) уже созданного администратора наполнение не трогает; логин сотрудника организации отметка не сбрасывает. Пароль другого администратора платформы Админка не сбрасывает.
- Вручную (локально или с доступом к базе): организацию с владельцем — `pnpm db:create-org --name … --inn … --owner-fio … --owner-login …` (ролью приложения, `DATABASE_URL`), администратора платформы — `pnpm db:create-admin --login …` (владельцем схемы, `DATABASE_ADMIN_URL`). Временный пароль печатается один раз, при первом входе его нужно сменить; поэтому в GitHub Actions эти команды так не запускаются. Исключение — `pnpm db:create-admin --password-from-env` с `ADMIN_TEMP_PASSWORD`: пароль берётся из настройки, ни пароль, ни логин не печатаются, без пароля команда падает, уже созданного администратора команда не трогает; так первого администратора рабочего сайта создаёт выпуск (раздел «Рабочий сайт»).
- Демо-сотрудники (erkin — владелец, meerim — главный бухгалтер, alisher и другие — бухгалтеры) на стенде входят паролем из секрета `TEST_DEMO_PASSWORD`: `migrate-test.yml` передаёт его в `pnpm db:seed --update` как `DEMO_PASSWORD` (своя строка от 12 символов, на рабочем сайте не задаётся). Пока секрет ни разу не задан, войти в демо-организацию нельзя. Новый пароль начинает действовать после следующего запуска `migrate-test.yml` (Actions → Migrate test → Run workflow); каждый запуск возвращает демо-сотрудникам пароль из секрета. Удаление секрета вход не закрывает (старый пароль остаётся) — чтобы закрыть, секрет меняют на новое значение и запускают workflow; при смене пароля наполнение закрывает и открытые сеансы демо-сотрудников (с тем же паролем ничего не меняется и никого не выкидывает). Пароль короче 12 символов или `demo` наполнение не примет: шаг «Справочники, ГКЭД и демо-организация» станет красным с ошибкой `DEMO_PASSWORD`, и стенд не обновится, пока секрет не исправят.

## Как выходит версия
- Слияние PR в `main` → Vercel сам выкладывает `main` на `test.buhuchet.kg` (стенд с демо-организацией), миграции стенда применяет `migrate-test.yml`: `pnpm db:migrate`, `pnpm db:seed --update`, `pnpm storage:init` с `APP_ENV=staging`.
  - Слияние, сделанное `automerge.yml` токеном `GITHUB_TOKEN`, не запускает workflow на `push` в main (так устроен GitHub), но запуск `workflow_dispatch` разрешён: после слияния PR, который меняет `packages/db/` или `spec/data/`, `automerge.mjs` запускает `migrate-test.yml` сам. Слияние человеком запускает его через `push`; вручную — Actions → Migrate test → Run workflow.
  - Упал шаг «Корзина файлов» — в журнале код ответа хранилища и какую настройку проверить (`InvalidAccessKeyId` — нет такого ключа, `SignatureDoesNotMatch` — секрет не от этого ключа или регион не тот). Значения ключей в журнал не выводятся; лишние пробелы и перевод строки по краям ключей, региона и имени корзины отбрасываются.
  - Vercel выкладывает код одновременно с миграциями, поэтому миграции пишутся совместимыми со старым кодом (сначала добавить, потом убрать).
- Рабочий сайт — только по команде заказчика «выпускай»: повтор проверок, миграции рабочей базы, метка версии и перенос `production` на эту метку — workflow `release-production.yml` (раздел «Рабочий сайт»).

## Рабочий сайт `buhuchet.kg`
- Supabase: отдельная организация на Pro (в бесплатной организации стенда Pro сделал бы платными оба проекта), проект во **Frankfurt** (eu-central-1), Data API выключен, Enforce SSL включён; корзина `buhuchet` и ключи S3 — как у стенда. Подключения — через общий пул (`aws-1-eu-central-1.pooler.supabase.com`): выделенный пул и прямое подключение Pro-проекта (`db.<ref>.supabase.co`) — только по IPv6, у Vercel и GitHub Actions его нет. В конце строк — `?sslmode=require`.
- Vercel, проект `buhuchet` (тот же репозиторий, Root Directory `apps/web`): Settings → Environments → Production → Branch Tracking — **`production`**; Settings → Git → Ignored Build Step — «Only build production» (превью веток рабочий проект не собирает); Settings → Functions → Function Region — **`fra1`**. Переменные — как у стенда (раздел «Переменные окружения»), но `APP_ENV` = `production`, `APP_BASE_URL` = `https://buhuchet.kg`, `S3_REGION` = `eu-central-1`, свои `CRON_SECRET` и `TELEGRAM_WEBHOOK_SECRET`, свой бот. Домены `buhuchet.kg` и `www.buhuchet.kg` (Settings → Domains; записи DNS Vercel создаёт сам — серверы имён домена у Vercel) привязываются после первого выпуска: до миграций сайт с пустой базой показал бы ошибку.
- GitHub → Settings → Environments → `production`: Required reviewers — заказчик; «Allow administrators to bypass configured protection rules» — выключено; Deployment branches — Selected branches → **`main`** (выпуск запускается из main: в ветке `production` нет этого workflow, пока она не догнала main). Секреты окружения:
  - `PRODUCTION_DATABASE_ADMIN_URL` — пользователь `postgres.<ref>`, общий пул в режиме сеанса (порт 5432); `PRODUCTION_DATABASE_URL` — та же строка, что `DATABASE_URL` в Vercel (`buhuchet_web.<ref>`, порт 6543);
  - `PRODUCTION_S3_ENDPOINT`, `PRODUCTION_S3_REGION`, `PRODUCTION_S3_ACCESS_KEY_ID`, `PRODUCTION_S3_SECRET_ACCESS_KEY` — те же, что в Vercel;
  - `PRODUCTION_ADMIN_LOGIN`, `PRODUCTION_ADMIN_PASSWORD` — первый администратор платформы: логин строчными буквами (в журнале GitHub скрывает только точное значение секрета), пароль временный — случайная строка от 16 символов. Сразу после выпуска войти и задать свой пароль, затем секрет пароля удалить (повторный выпуск с отметкой уже созданного администратора не трогает);
  - `PRODUCTION_DEPLOY_KEY` — закрытый ключ развёртывания. Ключ создаётся у заказчика (`ssh-keygen -t ed25519 -C buhuchet-release -f buhuchet-release`, без пароля): открытый (`buhuchet-release.pub`) — Settings → Deploy keys → Add deploy key, «Allow write access»; закрытый (`buhuchet-release`, целиком) — в этот секрет; файлы потом удалить. Им workflow пушит метку и ветку `production`: токен Actions (`GITHUB_TOKEN`) не может сдвинуть ветку на коммиты, которые меняют `.github/workflows`.
- Settings → Rules → Rulesets → New branch ruleset `production` (Active, Target — ветка `production`): Restrict updates, Restrict deletions, Block force pushes; Bypass list — только **Deploy keys**. Так ветку `production` (а значит, рабочий сайт) двигает только выпуск с одобрения заказчика: ни участник с записью, ни сессия Claude Code, ни инструменты GitHub в обход workflow её не сдвинут. Без этого правила (Restrict updates, Restrict deletions, Block force pushes) workflow выпуск не начинает. `PRODUCTION_DEPLOY_KEY` — единственный ключ развёртывания с записью: обход «Deploy keys» действует для всех ключей репозитория. Ветку `main` стоит так же закрыть Ruleset (Require a pull request, Block force pushes, Restrict deletions; без Deploy keys в Bypass list), иначе ключ с записью мог бы пушить в неё напрямую. В сессиях Claude Code дополнительно push в `production`, правку `git/refs/heads/production` и одобрение запуска (`pending_deployments`, `approveDeployments`) останавливает хук `.claude/hooks/guard-bash.mjs`.
- Коннекторы сессий Claude Code к Vercel и Supabase рабочий проект не меняют: выкладка, откат, переменные и база рабочего сайта — только через выпуск и настройки заказчика. Хук видит только команды терминала, поэтому надёжнее не давать коннекторам доступа к рабочему проекту Vercel и к организации Supabase рабочей базы.
- Перед слиянием PR, который убрал `regions` из `apps/web/vercel.json` (06.11.2026), у `buhuchet-kg` должен стоять Function Region `dub1`: иначе функции стенда уйдут в регион по умолчанию (Вашингтон), вдали от базы.
- Резервные копии: ежедневные копии базы Supabase Pro (Database → Backups, 7 дней); своей ночной копии базы и файлов пока нет (docs/deviations.md п. О-8).
- Ветка `production` создана 06.11.2026 от первого коммита репозитория (в нём только README): до первого выпуска Vercel её не соберёт, а выпуск сдвигает её вперёд без перезаписи истории.
- Выпуск: Actions → **Release production** → Run workflow (ветка `main`; коммит — пусто, то есть последний коммит main; при первом выпуске — отметка «Создать администратора»), затем одобрить запуск (Review deployments → production → Approve). Workflow проверяет, что коммит из main и по нему зелёный полный CI (ночной прогон или Actions → CI → Run workflow на main), применяет миграции, наполняет справочники без демо-организации (`APP_ENV=production`), готовит корзину, по отметке создаёт администратора (пароль в журнал не печатается, уже созданного не трогает), ставит метку `release-<дата>-<время>` и переносит `production` на коммит — Vercel выкладывает рабочий сайт. После первого выпуска — привязать домены и проверить `https://buhuchet.kg/health`.
- Откат версии — Vercel → проект `buhuchet` → Deployments → Instant Rollback; ветку `production` назад workflow не двигает (миграции вперёд-совместимы, база не откатывается).
